# 内存受限情况下向量检索方案技术详解与对比

## 方案 A：SQLite FTS5 + sqlite-vec

### 1. SQLite FTS5 全文索引

FTS5 是 SQLite 内置的全文搜索扩展，通过虚拟表机制实现倒排索引。在混合检索架构中，它承担关键词精确匹配的角色。

**虚拟表创建与索引结构**

FTS5 虚拟表通过 `CREATE VIRTUAL TABLE ... USING fts5(...)` 创建，可对多个文本列建立联合索引。例如对 title、description、body
三列建索引后，FTS5 内部维护一个倒排索引（存储在 `%_data` 表中），支持词项级的快速查找。

FTS5 支持中文分词，需在编译时启用相应 tokenizer 或在查询时配合外部分词逻辑使用。

**BM25 排序与列权重调优**

FTS5 内置 BM25 实现，通过 `bm25()` 函数返回相关性分数。默认 `ORDER BY rank` 等价于 `bm25()` 使用均匀列权重。

关键调优手段是显式指定列权重。`bm25(table, w1, w2, ..., wn)` 中的权重参数按列声明顺序对应，权重越高的列对最终排名影响越大。例如将
title 权重设为 10.0、artist 设为 3.0，可显著提升标题匹配的优先级。

需要注意的是，FTS5 的 `bm25()` 返回负值——数值越小（越负）表示越相关，因此调用方应使用升序排序（默认行为）。权重机制与
PostgreSQL 的 setweight 方案可保持一致，便于多后端统一排序逻辑。

**两阶段查询优化**

在高基数结果集场景中，推荐使用两阶段查询：第一阶段通过 CTE 先对 FTS5 索引执行 MATCH + LIMIT，获取候选 rowid；第二阶段再 JOIN
主表取回完整数据。这可避免 FTS5 对全量匹配行做排序后再 LIMIT 的性能问题。

**父块原文的存取设计**

在父子分块架构中，FTS5 索引建立在子块上（用于精确匹配），检索命中后通过 `parent_id` 回查父块原文。SQLite 中父块原文存储在普通表里，通过索引
`idx_blocks_parent_covering(parent_id, ...)` 加速回查。也可以在需要时使用递归 CTE 沿 `parent_id` 向上遍历获取完整的祖先链。

### 2. sqlite-vec 向量索引

sqlite-vec 是一个 SQLite 扩展，以虚拟表（`vec0`）形式提供向量相似度搜索，所有数据存储在 SQLite 文件内，内存占用极低。

**vec0 虚拟表与 KNN 查询**

创建方式为
`CREATE VIRTUAL TABLE vec_documents USING vec0(document_id integer primary key, contents_embedding float[768])`。查询时使用
`WHERE embedding MATCH :query_vector AND k = 10` 的语法触发 KNN 搜索，返回 `rowid` 和 `distance`。

`vec0` 的查询计划通过 `idxStr` 编码——一个由单头字符和若干 4 字符块组成的字符串，其中 `argv[i]` 承载查询向量，
`VEC0_QUERY_PLAN_KNN` 标识 KNN 查询类型。

每个 `vec0` 虚拟表有一个 shadow table 存储数据集标识、文档 ID、内容、元数据和 embedding，通用索引 blob 持久化在共享的
`vector_storage` 表中，并按数据集分片。同时存在内存缓存以加速查询。

**Rescore ANN 索引（二进制量化重排）**

sqlite-vec 最新实现了 `rescore` ANN 索引，将输入向量量化为 int8 或 bit 向量，在小向量空间上执行过采样 KNN
搜索，然后用全精度向量对结果重新打分。语法为 `indexed by rescore(quantizer=bit, oversample=8)`——先用二进制量化向量做汉明距离粗筛（取
`k * oversample` 个候选），再用原始 float 向量精排。全精度向量存储在 key-value 表中而非 vec0 的 chunked storage，重排阶段只需
B-tree 查找，读取速度约提升 10–15%。

**在混合检索中的角色**

在方案 A 的架构中，sqlite-vec 不是第一级召回器。流程是：FTS5/BM25 先召回 100–500 条候选，再对这些候选用 sqlite-vec
做向量相似度计算，或者直接用 bge-reranker-v2-m3 重排。这种设计使得 sqlite-vec 的 ANN 搜索范围极小，速度问题被大幅缓解。

### 3. BGE-M3 与 bge-reranker-v2-m3

**BGE-M3（嵌入模型）**

BGE-M3 是多语言嵌入模型，用于建库时编码子块、查询时编码 query。建库可分批处理，不需要常驻内存。

**bge-reranker-v2-m3（重排序模型）**

这是一个基于 bge-m3 的交叉编码器重排序模型，以 query 和 document 为输入直接输出相似度分数，可通过 sigmoid 映射到 [0, 1]
区间。模型规模约 2.3GB，推理仅需约 2GB 显存。

性能数据：在 Tesla T4 上，单个 query + top10 文档重排序平均耗时 <150ms。CPU 推理随文档数量线性扩展，短 pair 延迟远低于长文档截断场景。使用
`use_fp16=True` 可加速推理，GPU 上 fp16 与原模型速度相当或更快。

重排序模型设计上应仅用于对少量候选（数十到数百条）做精排，不宜直接用于大规模检索。

### 4. 混合检索流程与 RRF 融合

方案 A 的整体流程：FTS5/BM25 精确召回 → sqlite-vec 向量相似度 或 bge-reranker-v2-m3 重排 → 按 parent_id 取回父块原文。

当 FTS5 和向量检索并行执行时，两路结果需要融合。RRF 是标准方案：对每个文档在每路结果中的排名计算 `1/(k + rank)` 并求和，k
通常取 60。

在实现细节上，需要注意：abstain 门槛应基于原始向量分数而非 RRF 排序分数；FTS5 查询使用 OR 连接词项并去除停用词，防止常见词淹没
BM25 信号；FTS5 需在所有写路径上同步（upsert、reindex 等）。

## 方案 B：LanceDB + Tantivy



### 1. LanceDB 向量检索

LanceDB 是基于磁盘的列式向量数据库，使用 Lance 列式格式存储数据，支持 IVF-PQ 索引。其核心设计取向是磁盘优先——用 RAM
换延迟。在单线程基准测试中，LanceDB 的 QPS 为 70（MedRAG-50k），是测试集中最低的，但 p95 延迟约 22ms，仍在可接受范围内。

在索引构建方面，LanceDB 通过激进的默认量化策略实现快速索引构建，但这也导致检索质量有所牺牲。相较于 FAISS，LanceDB 用约 11
倍更快的索引构建时间换取召回率的一定下降。

### 2. Tantivy 全文索引

Tantivy 是 Rust 实现的全文搜索引擎库，类似 Lucene 的架构。LanceDB 将其作为 FTS 引擎集成，通过
`tbl.create_fts_index('text')` 为指定列创建全文索引。

Tantivy 使用 BM25 排序算法，支持中文分词（可结合 jieba 等分词器）。

### 3. 混合检索 API

LanceDB 原生支持混合检索，通过 `table.search(query, query_type="hybrid")` 调用。内部自动处理 FTS 索引 + 向量索引的并行查询，并使用
RRF（或 LinearCombination）进行分数融合。默认 RRF 的 K 值为 60，可通过 `RRFReranker(K=...)` 调整。默认融合策略是
LinearCombination，向量权重 0.7、全文权重 0.3。

支持 `prefilter` 参数在检索前按标量条件过滤（如 `.where("category = 'film'", prefilter=True)`）。也支持自定义 reranker，如
Cohere Reranker 或 CrossEncoder。

### 4. 数据分库设计

方案 B 建议按领域分库（如中医.lance、社科.lance），Agent 根据查询意图按需打开对应库。这与多索引路由的思路一致——不同查询类型可能需要不同的搜索配置权重。


## 方案 C：Qdrant 本地模式（mmap）

### 1. 内存层级体系

Qdrant 提供三级内存管理，不是简单的“内存 vs 磁盘”二元选择：

- **Pinned（固定）** ：常驻堆内存，不会被换出，访问最快。
- **Cached（缓存）** ：内存映射并在启动时预热到 OS page cache，初始速度快，但内存压力下可被 OS 换出。
- **Cold（冷存储）** ：内存映射但不预热，首次访问从磁盘读取。

关键约束：dense vectors 和 payloads 不能被 pinned；sparse vector 结构有独立规则。

### 2. mmap 配置方式

有两种方式启用内存映射存储：

**方式一：创建集合时设置 `on_disk`**

在集合创建 API 中为向量设置 `on_disk=true`，所有向量立即存储在 mmap 存储中。

**方式二：设置 `memmap_threshold`**

设置阈值后，超过该大小的 segment 自动转换为 mmap 存储。默认 `indexing_threshold` 为 20000，均衡场景下可将
`memmap_threshold` 设为相同值。同时可设置 `hnsw_config.on_disk=true` 将 HNSW 图也放到磁盘。

Python 示例：

python

```
vectors_config=models.VectorParams(size=768, distance=models.Distance.COSINE),
optimizers_config=models.OptimizersConfigDiff(memmap_threshold=20000)
```

### 3. 量化与内存层级组合

量化是让 cold 和 pinned 层级在真实规模下可行的关键。将向量压缩为 int8 或更低精度后，可以用固定的少量 RAM
容纳压缩副本，搜索时大部分候选只与压缩副本计算距离。Binary 量化和低精度 TurboQuant 默认启用 rescoring。

五种典型配置及其预期表现：

| 配置                             | 速度     | 内存占用 |
|:-------------------------------|:-------|:-----|
| Full Cached, No Quantization   | 快      | 高    |
| Full Cached, With Quantization | 快      | 高    |
| Full Cold, No Quantization     | 慢且不可预测 | 低    |
| Full Cold, With Quantization   | 中等     | 中等   |
| Pinned Quantized Vectors       | 快      | 固定中等 |

其中 **Pinned Quantized Vectors** 是 Qdrant 官方推荐的低内存高速方案：dense vectors 保持 cold，但量化压缩副本显式 pinned 在
RAM 中。这对应用而言是固定的内存开销，适合 16GB 甚至更低内存的机器。

### 4. 部署方式

Qdrant 本地模式可通过 Docker 或二进制部署。相比 SQLite 的零依赖单文件方案，部署复杂度更高，需要管理服务进程、配置文件和存储目录。

## 整体方案对比

### 对比维度总览

| 维度          | 方案 A：SQLite FTS5 + sqlite-vec   | 方案 B：LanceDB + Tantivy             | 方案 C：Qdrant mmap           |
|:------------|:--------------------------------|:-----------------------------------|:---------------------------|
| **核心引擎**    | SQLite FTS5（全文）+ sqlite-vec（向量） | LanceDB（向量）+ Tantivy（全文）           | Qdrant 一体化（向量+过滤）          |
| **存储形态**    | 单文件 SQLite                      | Lance 列式文件 + Tantivy 索引文件          | 多文件 mmap（服务化）              |
| **内存下限**    | 8GB 可跑，16GB 充裕                  | 磁盘优先，内存需求取决于工作集                    | 取决于层级配置，Pinned 量化方案约固定中等内存 |
| **纯向量检索速度** | 较慢（非内存索引）                       | 最慢（磁盘优先）                           | 最快（优化充分时）                  |
| **混合检索支持**  | 需自行编排（FTS5 → vec/reranker）      | 原生 `query_type="hybrid"`，内置 RRF    | 需自行编排（Qdrant 向量 + 外部 FTS）  |
| **部署复杂度**   | 最低（嵌入应用，零依赖）                    | 低（嵌入式库）                            | 较高（Docker/二进制 + 服务管理）      |
| **多租户/分库**  | 多 SQLite 文件                     | `.lance` 分库，Agent 按需打开             | 多 collection               |
| **重排序集成**   | bge-reranker-v2-m3 直接对接         | RRF/LinearCombination/自定义 reranker | 需自行接入 reranker             |
| **适合数据规模**  | 百万级以下                           | 3GB 级                              | 千万级可扩展                     |
| **运维成本**    | 极低                              | 低                                  | 中高                         |

### 混合检索流程对比

**方案 A 流程**：FTS5/BM25 召回 100–500 候选 → sqlite-vec 向量相似度 或 bge-reranker-v2-m3 重排 → 按 parent_id
取父块原文。每步都基于 SQLite 原生能力，数据不出库。

**方案 B 流程**：`table.search(query, query_type="hybrid")` 一行调用，LanceDB 内部完成 Tantivy FTS + 向量检索 + RRF
融合。开发者代码量最少，但对融合策略的细粒度控制较弱。

**方案 C 流程**：Qdrant 执行向量检索（可带标量预过滤）→ 如需全文检索需额外引入 FTS 引擎（如 Tantivy 或 Elasticsearch）→
应用层融合。Qdrant 本身不内置全文索引，混合检索需自行搭建。

### 选型建议

**方案 A 的适用场景**：内存受限（8–16GB）、数据规模在百万级以下、追求最低运维成本。SQLite 单文件方案的最大优势是“一个文件就是整个系统”——FTS5
索引、向量索引、父块原文都在同一个数据库文件中，备份、迁移、调试都极其简单。缺点在于纯向量检索速度受限于非内存索引，但通过 BM25
先召回大幅缩减候选集后，这个短板被有效规避。

**方案 B 的适用场景**：需要处理 3GB 级数据、接受磁盘优先的性能特征、希望用最少代码获得混合检索能力。LanceDB 的原生混合检索
API 是三个方案中开发效率最高的。缺点是纯向量检索速度在基准测试中排名靠后，且对融合策略的细粒度控制不如方案 A 灵活。

**方案 C 的适用场景**：数据规模大（千万级）、对向量检索延迟要求高、已有全文检索基础设施或愿意额外搭建。Qdrant
的内存层级体系提供了最精细的资源控制能力，Pinned Quantized Vectors 配置在保证速度的同时将内存占用固定在可控范围内。代价是部署和运维复杂度显著高于前两者。
