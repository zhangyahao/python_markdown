# 判别与验证：把"让谁来判断"这件事拆开

> 起因：2026-10-26 的一篇论文说"这类任务机器学习比 LLM 更合适"，2026-10-29 的另一篇说"LLM 辅助评审把假阳性从 23% 降到 6%"
> 。两条结论看起来互相打架。
> 本文的答案是：它们不打架，因为它们判断的是**两种不同的东西**。真正决定"该不该交给模型"的，不是模型的强弱，而是这个判断**有没有
oracle**。
> 整理日期：2026-11-02

---

## 0. 一句话结论

**判别**（在封闭标签集上分类）和**验证**
（判定开放形式的断言是否成立）是两种数学结构不同的任务。前者有大量标注、边界可学、需要校准过的概率——判别式小模型完胜；后者标签空间开放、正例不可枚举——只能靠能读语义的模型，并用形式化/可执行工具把能判定的部分接走。

把这两件事混在一个词里（都叫"评审"、都叫"分类"），就会得出"结论又变回去了"的错觉。

## 2. 判别与验证不是"两种任务"，是"两种判定策略"

> **修订 2026-11-02（用户指出）**：初版把"判别 / 验证 / 评估"写成了三种任务，这是错的。多分类 = K 个 one-vs-rest 二分类，所以"
> 这张工单该派给谁"既能被描述成判别，也能被描述成验证——数学上完全等价。**用任务形态当划分轴是无效的。** 下面换轴。

### 2.1 区别在"判定那一刻，真值能不能被独立拿到"

- **验证** = 现场调用 oracle：执行一个过程，它直接告诉你对错。
- **判别** = 用统计近似替代 oracle：等不到真值，只能用过去的真值样本，学一个"看起来像哪一类"的映射。

同一张工单，两种读法都成立，区别只在**判定时点**：

| 两种问法                  | 判定发生在      | 真值来源                | 归入               |
|-----------------------|------------|---------------------|------------------|
| "这张单**此刻**该派给谁？"      | 派单前，必须立刻决定 | 没有真值，只有 47,837 条历史单 | **判别**（学近似）      |
| "这张单**三天后**回头看，派对了吗？" | 处理完之后      | 是否被转派、解决时长、是否二次分派   | **验证**（调 oracle） |

论文 A 做的是左边那个。**不是因为它选对了方法，而是因为右边那个在当时不可得**。

### 2.2 oracle 的严格定义

原义来自计算理论：oracle 是一个黑盒，喂它一个问题，它直接给正确答案（图灵 1939 的 oracle machine；PAC 学习里的 membership
query 同源）。不需要理解它为什么对，只需要能调用。

在本语境下，一个东西要算 oracle，必须同时满足：

| 条件            | 含义           | 反例                  |
|---------------|--------------|---------------------|
| **单实例回答**     | 对"这一个"样本给出对错 | 整体准确率 87% 不是 oracle |
| **独立于被评判的模型** | 判定源不是它自己     | 让同一个 LLM 判断自己写得对不对  |
| **可复现**       | 同输入，同输出      | 人来评，两次结论可能不同        |

三种实际形态：

1. **形式化检查器**：Lean kernel、SMT 求解器、类型系统——执行即知真假。
2. **可执行检查**：跑测试、跑 PoC、差分重放——看退出码与 before/after 差异。
3. **真实世界反馈**：工单后来有没有被转派、用户有没有点踩、A/B 实验指标。

**最关键的一句：历史标注不是 oracle，是 oracle 的快照。** 它记录过去的真值，只覆盖旧分布的一部分，且对此刻要判的新实例**不提供答案
**。把十万条历史标注压缩成一个映射，得到的是判别器。"用历史标注训练的模型"与"现场问 oracle"是两件事：前者是**从 oracle
的历史输出里学一个近似**，后者是**每次都现场问**。

### 2.3 两个轴、四个格子

**轴一：真值什么时候能拿到？**（当场 / 短期可回 / 长期或不可得）
**轴二：答案空间封闭吗？**（固定标签集 / 开放形式）

|                 | 真值可当场（或短期内）获得                     | 只能靠历史快照                        |
|-----------------|-----------------------------------|--------------------------------|
| **空间封闭**（固定标签集） | **直接调 oracle**；也可学近似以求快（但要知道自己在赌） | **判别式小模型** · 需监控漂移             |
| **空间开放**（自由形式）  | **oracle + 模型做翻译/构造证据**（模型不下结论）   | **没有好办法**：只能评估 + 人工兜底，误差预算必须进账 |

四格对应四种做法，"用 LLM 还是用小模型"每格答案不同。

三件事的落位：

| 任务     | 真值何时可得          | 空间      | 落位 | 所以                    |
|--------|-----------------|---------|----|-----------------------|
| 工单分派   | 3 天后（是否被转派）     | 封闭（8 类） | 右上 | 等不起，只能学近似 → 小模型       |
| 数学证明审核 | 当场（Lean kernel） | 开放      | 左下 | 等得起 → kernel 判定，模型只翻译 |
| 代码回归检测 | 当场（跑 PoC）       | 开放      | 左下 | 等得起 → 程序判定，模型只写证据     |

这样就解释了两个"矛盾"结果：论文 A 站在右上格，论文 B 站在左下格。**格子不同，最优解自然不同。**

### 2.4 关于"评估"

评估不是第三类任务，而是"无 oracle 且分布开放"
这一格（右下）的不得已做法：没有真值、正例不可枚举，只能给质量分并接受残余误差。它不能升级成"确认"，只能标为"
经人工/多视角复核"。

## 3. 为什么判别上小模型赢

### 3.1 原文数字

语料：47,837 条工单、8 类。成本模型 (c_ok, c_triage, c_wrong) = (0, 1, 5)，即错误路由的代价是人工分派的 5 倍。

| 项目                                     | 数值                                                                          |
|----------------------------------------|-----------------------------------------------------------------------------|
| TF-IDF + 逻辑回归，阈值 0.60（在标定集上选中）         | 测试成本 **0.763 → 0.472**，相对下降 **38.1%**（配对比率 bootstrap 95% CI [35.7%, 40.4%]） |
| 错误路由率                                  | **15.3% → 3.5%**                                                            |
| 冻结的标定策略 vs always-route / always-defer | 在 16 个设置中 **14 个**更优（事后成本参数分析）                                              |
| fine-tuned DistilBERT（分层 1,000 条测试子集）  | 准确率 **0.879**                                                               |
| 最强 prompt 配置（同一子集）                     | 准确率 **0.477**                                                               |
| isotonic 重校准                           | 降低 ECE，但**不改善判别**                                                           |
| GPT-4o-mini few-shot                   | 重校准前后**只有一个置信值**，正确性 AUROC **0.500**                                        |
| 解析推导的盈亏平衡概率 0.80 处                     | 7 个 prompt 配置**全部弃权**；Haiku few-shot 只路由 19/1000                            |

### 3.2 机制：为什么必然如此

1. **标签集封闭 → 标注可积累 → 判别边界可学。** 8 个类、4.7 万条历史，TF-IDF 这种近乎零成本的特征就足够把边界画准。这里没有"
   理解语义"的需求，只有"这个文本更像哪个队列"。
2. **成本不对称 → 阈值本身就是可优化对象。** 因为有校准集和明确的成本函数，阈值 0.60 是**算出来的**，不是调的。LLM 的 prompt
   没有这个旋钮——你没法让一次生成"输出一个阈值 κ"。
3. **LLM 的置信度不是概率。** 这是最硬的一条：isotonic 把 ECE 压下去了，但判别没变好；GPT-4o-mini few-shot
   重校准前后都只有一个自信值，AUROC 恰是 0.500（等于抛硬币）。也就是说，**你拿不到一个能用于阈值决策的概率**。论文因此建议同时报告
   AUROC 与 tie-aware risk-coverage area，而不是只看 ECE。

### 3.3 这条结论的适用边界（作者自己划的）

作者明确写了 scope：单一数据集、特定 prompt 设计、特定模型端点、示例性成本模型；这项工作**是一个评估框架，不是一种新的弃权算法，也不构成通用的部署认证
**。

所以正确的读法是：**在"封闭标签集 + 成本可量化 + 需要校准概率"的条件下，判别式小模型是默认选择**。不是"LLM
在分类上全面不行"。

## 4. 为什么验证上 LLM 有用

### 4.1 为什么这里不能"训个分类器"

Ramanujan Challenge 的题目是数论领域的研究级问题，包含**未发表的结果与公开猜想**；给出的是数学常数的具体公式（正确性可数值抽查），但证明需要非平凡的数学。

三个理由让分类器路线直接不可行：

1. **正例不可枚举**：正确的证明有无数种写法，你无法造出一个覆盖"正确证明"分布的标注集。
2. **正确性依赖语义**：形式相同但一步论证不成立的证明，在字符层面几乎无法区分。
3. **分布开放**：新问题、新技巧不断出现，训练集永远落后于测试集。

判别式模型学的是"在这批正例和这批负例之间怎么划线"，而这里的问题是"这个论证是否成立"——后者不是分类问题。

### 4.2 原文数字与其正确读法

| 项目                        | 一次性 LLM 判定 | AI 辅助管线 |
|---------------------------|------------|---------|
| 自然语言证明的**假阳性判定率**         | 23%        | **6%**  |
| 配套代码（CAS / Lean）判定**准确率** | 46%        | **58%** |

管线覆盖三种提交格式：自然语言证明、CAS 代码、Lean 形式化，评估语义与逻辑正确性。

**两个读法都很重要：**

- **读法一（对比基准）**：6% 的对手是 23%，不是某个分类器。所以这是"管线 > 单次 LLM"，不是"LLM > 传统 ML"。作者的贡献是给"没有
  checker 的那部分"找到可用的降级方案。
- **读法二（论文内部的印证）**：**有 checker 的那一侧明显强于纯语义那一侧**（代码 58% vs 自然语言 23%→6%）。这恰好和论文 A
  是同一个方向——凡是有机械校验的地方，把判定交给程序都更好。

另外，6% 是**残余错误率，不是零**。这一点常被引用时丢掉。

## 5. 判据的落地形态：从两轴到四档

> 本节是第 2.3 节四格的具体化——**第 2 节给轴，这里给每档的操作细节**。

按顺序问三个问题，就能定位到格子：

1. **这个判断的真值，什么时候能知道？** 立刻 / 几小时后 / 永远不知道。
2. **我能等到那时候吗？** 业务上必须当场给答案 → 判别格；能等 → 验证格。
3. **等不到时，历史样本够不够、分布稳不稳？** 够且稳 → 小模型；不够或稳不住 → 只能评估 + 人工，且必须写清残余误差。

三问落到具体 oracle 形态上，就是下面四档：

| 档位                 | oracle 形态                      | 该用什么                            | 典型做法                              | 残余风险                              |
|--------------------|--------------------------------|---------------------------------|-----------------------------------|-----------------------------------|
| **A. 有形式化 oracle** | Lean / Coq / SMT / 类型系统 / 规格检查 | 完全自动化判定，模型只负责**翻译**（自然语言 → 形式化） | 证明 → Lean kernel 检查；策略 → 约束求解     | 形式化本身可能写错或不忠实（"证明了一个不是原问题的东西"）    |
| **B. 有可执行 oracle** | 测试 / PoC / 差分重放 / 性能阈值         | 程序判定，模型负责**构造证据**（写 PoC、写复现脚本）  | 退出码 + before/after 差异 + bisect 定位 | oracle 的**覆盖率**是假设：没测到的行为改坏了也判不出来 |
| **C. 无 oracle**    | 无                              | 只能评估，模型 + 人工，**必须带误差预算**        | 多视角评审、交叉复核、把分歧显式列出                | 误差不可完全刻画；不得把结论标成"已确认"             |
| **D. 封闭标签 + 可学边界** | 历史标注                           | **判别式小模型**（不是 LLM）              | TF-IDF+LR / 微调编码器 + 校准阈值          | 分布外漂移；ECE 好看但 AUROC 不动的陷阱         |

档位 D 是个特例：它有"统计意义上的 oracle"（历史标注），所以能用有监督学习。而 A/B 是"逻辑意义上的 oracle"——判定是确定的，不靠统计。

## 6. 六个真实系统，把判据压上去

### 6.1 Trail of Bits `regression-hunt`：oracle 存在，但覆盖率有限

- 判据位置：**档位 B**。它有活 PoC、before/after 可观测差异、bisect 定位三重断言。
- 战绩：130+ 个已合并 PR 中挖出 21 个回归（16 功能 / 1 性能 / 4 构建测试，无破坏安全防护）；单次运行 58 个候选确认 21 个（**约
  36% 精度**）。
- 为什么 36% 还能用：因为假阳性比"直接让 Codex 审 PR"低 **25%**（95% CI 14–38%），且**允许 `inconclusive`**
  ——判不了的明说判不了，而不是硬给结论。
- 四原则里最关键一条：**每条结论必须有活的 PoC**。没有 PoC 就不许说"确认"。

### 6.2 regguard：把 `unknown` 与 `False` 分开

- 判据位置：**档位 B + C 的边界**。
- 三队列设计：`candidates`（规则全真）/ `review`（含 unknown，必须人工看）/ `dropped`（有否决规则为 False）。
- 核心工程约束：**非 Python 语言的可达性/覆盖率一律标 `unknown`，绝不标 `False`**。因为 `False` 意味着"
  我已证明它不构成回归"，而 `unknown` 只意味着"我不知道"。
- 这条约束的代价是 review 队列会变长；收益是**报告不会说谎**。之前版本把非 Python 改动在枚举阶段直接过滤掉，结果是"候选 0
  条但确认回归 1 条"——人会读候选区，于是成了假阴性。

### 6.3 Copilot Fusion 的 Cascade：judge 就是 gate，收益随可验证性摆动

- 判据位置：**档位 B 的编排应用**。Cascade = 便宜模型先出草稿 → judge 判定是否接受 → 不接受则交给 repair model。
- 收益证据（Artificial Analysis Coding Agent Index v2.0，Max 档）：Terminal-Bench 4.0 **71 分，全场第一**——这类任务可通过执行验证，judge
  判得准，编排就赚。
- 亏损证据：FrontierCode **51 分，第三**（落后 Opus 5.5 的 56、Devin Fusion 的 54）；SWE-Atlas-QnA-AA **57 分，明显落后**
  ——这两类需要连续深度判断与自我提问，judge 判不准，Cascade 反而拖累。
- **一句话**：**任务越可验证，编排越赚；越依赖不可判定的判断，编排越亏。**

### 6.4 QERA（[arXiv:2610.35083](https://arxiv.org/abs/2610.35083)）：用代码兜住能兜的部分

- 判据位置：**档位 C，但把其中可计算的两个环节交给了程序**。
- 做法：先把请求拆成需求清单和带类型的信息需求，**用代码过滤以保证忠于用户原话**；作答后再问一遍并**用代码校验引文**。
- 战绩：405 个任务 × 4 个前沿 LLM，QERA 在每个 LLM 上都最高，平均 **21.0%**（最强推理期基线 18.2%，直接作答 14.6%）；token 用量仅为
  Ctx2Skill 的 **4–5%**。
- 消融显示收益在作答前就已确定：固定作答协议 +3.8 分、请求特定问题 +1.6 分；事后检查主要修数字类要求。
- **要点**：即使整体任务不可判定，也能识别出子环节并交给代码——**"用代码过滤"和"用代码校验引文"都是档位 A/B 的碎片**。

### 6.5 ShallowDefend（[arXiv:2610.40627](https://arxiv.org/abs/2610.40627)）：把不可判定的东西改成可解析的

- 判据位置：**把档位 C 往档位 B 推**。
- 做法：Assess → Decide → Respond。先让模型对用户意图做一个**显式、可解析的安全决策**，再据此生成回复；该决策用 RL 在 payload
  回合训练，奖励可以是**规则式自校验**，不需要 judge，也不需要人工标注。
- 关键洞察：安全性无法被"判定"，但可以被"约束成结构化输出 + 规则校验"。这是把不可判定任务**改写**成可判定任务的标准手法。

### 6.6 TextSeal2（[arXiv:2610.40613](https://arxiv.org/abs/2610.40613)，Meta FAIR）：检测是统计检验，不是让模型"觉得像"

- 判据位置：**档位 D 的近亲**——有明确的统计判据（FPR 门槛）与可测指标（检出率）。
- 做法：让被拒绝草稿替换掉的 token 仍带同样密钥，接受率不变；多密钥合并为单一虚拟密钥用 Gaussian copula 耦合。
- 战绩：同等多样性下，100 token 回答的检出率比 TextSeal 高 **8–22pp**（FPR 1e-3）；投机解码下 200 token 比 TextSeal 与
  textGrain 分别高 **18/22pp**。
- **要点**：它从不说"这段文本看起来是 AI 生成的"，只说"在 FPR = 1e-3 下，100 token 能否检出"。**把结论写成带门槛的检验，而不是印象。
  **

## 7. 反模式清单

| 反模式                         | 机制                  | 症状                                      |
|-----------------------------|---------------------|-----------------------------------------|
| **拿 LLM 当闭集分类器**            | 没有可优化的阈值，置信度不是概率    | 准确率腰斩（0.477 vs 0.879），阈值调不动，AUROC 0.500 |
| **拿分类器当验证器**                | 正例不可枚举，训练集永远落后      | 分布外直接崩，且崩的时候毫无预警                        |
| **把"LLM 说对"当验证**            | 一次性判定有 23% 假阳性量级    | 生产事故率 = 假阳性率                            |
| **用 ECE 改善冒充判别改善**          | 校准与判别是两件事           | 报告很漂亮，混淆矩阵没变                            |
| **过滤掉判不了的样本**               | 枚举阶段丢弃 = 假阴性        | "候选 0 条但确认回归 1 条"                       |
| **把提示词当约束**                 | 提示词能表达意图，不能表达约束     | Anthropic 禁克隆游戏：误伤原创者，换模型/拆任务即绕过        |
| **用 judge 的分数当门槛但不测 judge** | 编排收益完全取决于 judge 准确率 | 可验证任务赚、开放判断亏，且亏损不可见                     |

## 8. 落地检查表

第 5 节的三问用来**定位格子**；格子定下来之后，用下面五问**设计实现**。

1. **标签集是封闭的吗？** 是 → 走档位 D（小模型），并且**先去看有没有历史标注**。不是 → 继续。
2. **错的代价可量化、且不对称吗？** 是 → 成本模型可以写出来，阈值可以优化。这是档位 D 能否成立的关键前提。
3. **存在可执行或形式化的 checker 吗？** 有 → 档位 A 或 B，模型只负责**构造证据**（写 PoC、写形式化、写复现脚本），不负责下结论。
4. **checker 的覆盖率是多少？** 覆盖不到的部分**必须显式标 `unknown`**，不许并入通过集合。这是最容易做错的一步。
5. **残余错误率能进预算吗？** 6% 假阳性、36% 精度——这些数字能不能接受，取决于下游有没有人工复核，而不是取决于模型。

五问全部回答完之后，"用 LLM 还是用小模型"往往已经不是问题了——**问题变成了"哪些环节有 checker，哪些环节必须人工兜底"**。
