## 经验库调用时机与规则路由的职责边界

  **文档版本**：v1.0
  **说明**：本文档为《Agent 长期记忆与经验管理系统》的补充章节，专门回答“经验库何时被调用”“简单查询是否存入经验库”“规则路由与经验库是否重复”三个核心问题，明确两者的职责边界与协作方式。

  ## 一、核心结论

| 问题              | 答案                  |
 |:----------------|:--------------------|
| 经验库什么时候被调用      | 只有规则路由无法完全决策的复杂请求才查 |
| 简单查询是否存入经验库     | 默认不存，只存异常和优化案例      |
| 规则路由 + 经验库是否多一步 | 简单请求不多；复杂请求多一步，但净收益 |

**核心原则**：
  1. **规则路由是必经步骤，经验库是条件触发。**
  2. **简单请求不查经验库，靠规则路由和缓存减少 LLM 调用。**
  3. **复杂请求查经验库，用毫秒级本地查询换 API token 节省。**
  4. **经验库不是减少 LLM 调用的手段，是优化 LLM 调用质量的手段。**

## 二、经验库的调用时机

### 2.1 不是所有请求都查经验库

| 请求类型                   | 走什么                  | 查经验库吗       |
    |:-----------------------|:---------------------|:------------|
| 简单事实查询（“黄芪性味归经”）       | 规则路由 → 混合检索 → 模板输出   | 不查          |
| 单领域标准问答（“甘肃黄芪种植条件”）    | 规则路由 → 混合检索 → 模板输出   | 不查          |
| 跨域复杂分析（“黄芪价格走势+种植建议”）  | 规则路由 → LLM API       | 查，注入相关经验    |
| 多步骤任务（“分析某地区地方病+中医辅助”） | 规则路由 → LLM API       | 查，注入相关经验    |
| 历史失败过的问题               | 规则路由识别 → 查经验库 → 决定路径 | 查           |
| 首次出现的新问题               | 规则路由无法判断 → LLM API   | 查，但可能无经验可注入 |

### 2.2 三个触发条件

经验库只在以下三个条件之一满足时触发：

**条件一：规则路由无法确定意图**

    - query 模糊
    - query 跨域
    - query 含歧义
    - query 是首次出现

**条件二：规则路由能确定意图，但无法确定最优路径**

    - 同一意图有多种处理路径
    - 历史上有成功/失败记录
    - 当前路径可能不是最优

**条件三：规则路由识别到“历史失败过”**

    - 该 query 或类似 query 曾失败
    - 需要避坑提示
    - 需要推荐替代路径

**三个条件都不满足时，不查经验库。**

### 2.3 完整决策流程



  ```text
  用户 query
     ↓
  规则路由（本地，毫秒级）
     ├── 简单请求 → 混合检索 → 模板输出 → 结束
     │                （不查经验库）
     │
     └── 复杂请求 → 查经验库（本地，毫秒级）
                      ├── 有经验 → 注入经验 → 调 LLM API
                      └── 无经验 → 直接调 LLM API
  ```

**只有复杂请求才多这一步。** 简单请求不查。

## 三、简单查询是否存入经验库

### 3.1 默认不存

简单查询的特征：

- 答案唯一或高度确定
- 检索路径固定
- 不需要 LLM 推理
- 重复率极高

**这类请求的经验没有价值**，因为：

- 路径已经固定，不需要经验引导
- 存进去只会让经验库膨胀
- 检索时还会增加噪声

### 3.2 值得存的例外情况

只有以下情况才值得存入经验库：

| 情况      | 例子                | 存什么               |
  |:--------|:------------------|:------------------|
| 查询曾失败过  | “某药材别名”检索不到       | 存“该别名对应标准名”       |
| 查询有歧义   | “黄芪”可能指药材或人物      | 存“该 query 应路由到中医” |
| 查询路径被优化 | 原来走 A 工具，现在走 B 更快 | 存“该类查询优先走 B”      |
| 用户多次纠正  | 用户反复说“不是这个意思”     | 存“该 query 的真实意图”  |

**简单查询默认不存，只存异常和优化。**

### 3.3 减少 LLM 调用靠什么

减少 LLM 调用**不靠经验库**，靠的是：

| 方式         | 作用            | 是否依赖经验库    |
  |:-----------|:--------------|:-----------|
| 规则路由       | 简单请求不走 LLM    | 不依赖        |
| 模板输出       | 简单请求不调 LLM    | 不依赖        |
| 结果缓存       | 相同 query 直接返回 | 不依赖        |
| BGE-M3 相似度 | 意图分类不调 LLM    | 不依赖        |
| **经验库**    | **复杂请求减少试错**  | 依赖，但只对复杂请求 |

**减少简单请求的 LLM 调用，靠规则路由和缓存，不靠经验库。**

**经验库的价值是：对已经要调 LLM 的复杂请求，减少 LLM 的试错次数和 token 消耗。**

## 四、规则路由与经验库的职责边界

### 4.1 两者不是替代关系

| 层次       | 规则路由                   | 经验库         |
  |:---------|:-----------------------|:------------|
| **作用**   | 判断请求类型、路由到对应处理链路       | 优化复杂请求的路径选择 |
| **触发条件** | 所有请求                   | 只有复杂请求      |
| **决策依据** | 关键词、规则、BGE-M3 相似度      | 历史成功/失败经验   |
| **输出**   | 请求类型、目标 Agent、是否需要 LLM | 推荐路径、避坑提示   |
| **成本**   | 毫秒级                    | 毫秒级（本地检索）   |
| **覆盖范围** | 已知模式                   | 未知模式、边界情况   |

**规则路由管“是什么”，经验库管“怎么做更好”。**

### 4.2 决策树



  ```text
  用户 query
     ↓
  规则路由能判断意图吗？
     ├── 能 → 能判断工具和数据源吗？
     │         ├── 能 → 直接执行，不查经验库
     │         └── 不能 → 查经验库，看是否有推荐路径
     │
     └── 不能 → 查经验库，看是否有类似历史
                ├── 有 → 参考经验，调 LLM
                └── 无 → 直接调 LLM
  ```

**只有规则路由无法完全决策时，才查经验库。**

### 4.3 具体例子

| Query         | 规则路由         | 经验库 | 结果         |
  |:--------------|:-------------|:----|:-----------|
| “黄芪性味归经”      | 识别为中医查询，工具明确 | 不查  | 直接检索       |
| “黄芪价格走势”      | 识别为经济查询，工具明确 | 不查  | 直接查经济数据    |
| “黄芪价格走势+种植建议” | 识别为跨域，工具不明确  | 查   | 注入经验，调 LLM |
| “分析某地区地方病”    | 识别为跨域，工具不明确  | 查   | 注入经验，调 LLM |
| “上次那个问题再问一遍”  | 无法识别意图       | 查   | 检索历史经验     |

## 五、成本对比

### 5.1 简单请求

| 方案                      | 成本                    |
  |:------------------------|:----------------------|
| 规则路由 + 混合检索 + 模板        | 本地毫秒级，无 API 成本        |
| 规则路由 + 查经验库 + 混合检索 + 模板 | 多一次本地查询，无 API 成本，但没必要 |
| **结论**                  | **不查经验库**             |

### 5.2 复杂请求

| 方案                         | 成本                          |
  |:---------------------------|:----------------------------|
| 规则路由 + 直接调 LLM             | API 成本高，可能试错多次              |
| 规则路由 + 查经验库 + 注入经验 + 调 LLM | 多 10ms 本地查询，但可能省 5000 token |
| **结论**                     | **查经验库，净收益**                |

### 5.3 为什么复杂请求值得多这一步

- 经验库查询是**本地 SQLite + 向量检索**，毫秒级
- 经验注入能**减少 LLM 试错**，节省的是 API token 和响应时间
- 对比：多花 10ms 查经验库，可能省下 5000 token 和 3 秒 API 时间
- **对复杂请求，这一步是净收益**

## 六、经验注入控制机制

### 6.1 注入 Token 预算

硬性规定：每次注入的经验不超过 **N 个 token**。



  ```text
  经验注入预算 = 1500 token
  单条经验上限 = 200 token
  最多注入条数 = 7 条
  ```

超出预算时，按置信度排序，截断。

### 6.2 置信度门槛

只有置信度 > 阈值的经验才注入。

| 置信度     | 处理                 |
  |:--------|:-------------------|
| > 0.8   | 可以注入               |
| 0.5–0.8 | 只作为参考，不注入，或标注“待验证” |
| < 0.5   | 不注入，仅存储            |

### 6.3 数量上限

| 经验类型     | 最多注入    |
  |:---------|:--------|
| Global   | 3 条     |
| Domain   | 3 条     |
| Personal | 1 条     |
| **合计**   | **7 条** |

### 6.4 去重与合并

- 检索到的经验先做相似度去重
- 相似度 > 0.9 的只保留置信度最高的一条
- 定期离线聚类合并同类经验

### 6.5 优先级排序

当候选经验超过预算时，按以下顺序排序：

1. 置信度
2. 情境匹配度（时间、地区、任务类型）
3. 最近使用成功率
4. 时间新鲜度

取前 N 条。

### 6.6 分层注入

| 层级          | 注入方式               | Token 成本 |
  |:------------|:-------------------|:---------|
| Global 经验   | System Prompt 固定片段 | 低，可缓存    |
| Domain 经验   | System Prompt 动态片段 | 中        |
| Personal 经验 | Few-shot 示例        | 中        |
| 低置信度经验      | 只在工具调用前作为提示        | 低        |

**Global 经验可以放在前缀稳定区，被 TokenPilot 缓存复用，几乎不增加边际成本。**

## 七、经验库增长与 Token 成本的关系

| 经验库规模     | 检索候选  | 注入 Prompt | Token 成本 |
  |:----------|:------|:----------|:---------|
| 100 条     | top 5 | 3 条       | 固定       |
| 1,000 条   | top 5 | 3 条       | 固定       |
| 10,000 条  | top 5 | 3 条       | 固定       |
| 100,000 条 | top 5 | 3 条       | 固定       |

**只要检索和注入有上限，经验库增长不改变 Token 成本。**

经验库增长只影响：

- 存储空间（SQLite 便宜）
- 检索时间（向量检索毫秒级，可接受）
- 合并和淘汰的维护成本

**不影响 Prompt 长度。**

## 八、多知识库场景下的经验管理

### 8.1 统一经验库，按 scope 分层

假设你有：

- 中医知识库
- 社科知识库
- 经济数据库
- 未来可能加法律、教育等

**经验管理应该是：**



  ```text
  一个统一经验库
     ├── Global 经验（所有领域共享）
     ├── Domain 经验（按领域分）
     │   ├── 中医
     │   ├── 社科
     │   ├── 经济
     │   └── ...
     └── Personal 经验（按 Agent 分）
  ```

**不是每个知识库一个经验库，而是一个经验库按 domain 分层。**

### 8.2 检索时只取当前领域相关

检索时：

- 取 global 经验 top 3
- 取当前 domain 经验 top 3
- 取当前 agent 经验 top 1
- 合计不超过 7 条

新增知识库只是新增一个 domain 分区，**不影响其他领域的检索和注入**。

### 8.3 经验库膨胀的应对

| 措施   | 说明                             |
  |:-----|:-------------------------------|
| 定期归档 | 超过 90 天未被命中的经验、置信度 < 0.3 的经验归档 |
| 聚类合并 | 相似度 > 0.85 的经验合并为一条            |
| 分层存储 | 活跃层、候选层、归档层三级                  |
| 硬性上限 | 活跃层经验数上限，超出时按置信度和新鲜度淘汰         |

## 九、总结

| 问题            | 答案                                  |
  |:--------------|:------------------------------------|
| 经验库会无限增长吗     | 会，但不影响 Token                        |
| 不同知识库会叠加经验库吗  | 不会，按 domain 分层，共享 global            |
| 会导致 Token 爆炸吗 | 只要注入层有预算和门槛，就不会                     |
| 真正会爆炸的场景      | 不做 top-k 限制、不做置信度过滤、不做去重、不做预算       |
| 怎么控制          | Token 预算 + 置信度门槛 + 数量上限 + 去重 + 分层注入 |
| 经验库增长影响什么     | 只影响存储和维护成本，不影响 Prompt 长度            |
| 简单请求查经验库吗     | 不查                                  |
| 复杂请求查经验库吗     | 查，净收益                               |
| 规则路由和经验库重复吗   | 不重复，规则路由管“是什么”，经验库管“怎么做更好”          |

**核心原则：存储可以无限，注入必须有限。**
**核心判断**：经验管理是“规模化收益”的工具，不是“小项目提效”的工具。它需要足够多的重复任务、足够好的验证信号、足够强的维护能力才能回本。小项目缺的正是这三样。
**经验库的定位**：不是让简单请求更快，而是让复杂请求更准、更省。它服务于已经要调 LLM 的请求，不服务于本地就能解决的请求。
