> 读者对象：准备用 LlamaIndex 做真实应用的工程师。

## 2.0 为什么这一章决定了应用的成败

RAG 应用的效果，90% 的人在调 prompt 和换模型，但真正的瓶颈几乎总在检索侧：召回不到正确的块，再强的模型也只能编。
而检索侧的所有问题——召回不准、延迟高、成本失控、数据更新错乱——都收敛到四个决策上：

1. **向量存在哪里**（存储层选型）
2. **文本怎么切、embedding 怎么算**（索引层设计）
3. **查询怎么发**（过滤、混合检索、重排）
4. **数据怎么进、怎么改、怎么删**（生命周期管理）

第 4 个最容易被忽略，却是在生产环境里最先爆炸的一个。

### 2.0.1 先记住 0.10 前后的断层

0.10 是 LlamaIndex 的一次大重构：单体包拆成了核心包 + 一堆集成包，`ServiceContext` 被 `Settings` 取代。你在网上搜到的教程，一半以上还是旧写法，粘过来会直接 ImportError。对照表：

| 用途 | 【0.10 前】旧写法 | 0.11+/0.12 现行写法 |
| --- | --- | --- |
| 向量库适配器 | `from llama_index.vector_stores import QdrantVectorStore` | `from llama_index.vector_stores.qdrant import QdrantVectorStore` |
| 全局配置 | `ServiceContext.from_defaults(...)` | `Settings.llm / Settings.embed_model / Settings.node_parser` |
| 文本切分 | `from llama_index.node_parser import SentenceSplitter` | `from llama_index.core.node_parser import SentenceSplitter` |
| 文档读取 | `from llama_index import SimpleDirectoryReader` | `from llama_index.core import SimpleDirectoryReader` |
| 提示词 | `from llama_index.prompts import ...` | `from llama_index.core.prompts import ...` |
| Embedding | `from llama_index.embeddings import HuggingFaceEmbedding` | `from llama_index.embeddings.huggingface import HuggingFaceEmbedding` |
| 自定义模块（回调/工具） | `llama_index.callbacks` 等 | 一律在 `llama_index.core.*` 下 |

安装时也要按需装，不要 `pip install llama-index` 一把梭（它会拉全量集成包，几百 MB 且版本互相牵制）：

```bash
pip install "llama-index-core>=0.11,<0.13" \
            llama-index-vector-stores-qdrant \
            llama-index-vector-stores-postgres \
            llama-index-vector-stores-chroma \
            llama-index-embeddings-huggingface \
            llama-index-embeddings-openai \
            llama-index-retrievers-bm25 \
            llama-index-postprocessor-cohere-rerank
```

【0.10 前】对应的包名是 `llama-index-vector-stores-qdrant` 的 0.1.x 系列，接口差异较大，别混装。

## 2.1 存储分层：LlamaIndex 到底把什么存在了哪里

这是最容易误解的地方。很多人以为「向量库存了所有东西」，于是把 docstore 关掉，结果后面想做去重、增量更新、父子块合并、引用回溯，全部做不了。

### 2.1.1 四个 Store 的职责

```
                         ┌─────────────────────┐
   原始文件 ──读──▶      │   Document 对象      │
                         └──────────┬──────────┘
                                    │ NodeParser 切片
                                    ▼
                         ┌─────────────────────┐
                         │   TextNode 列表      │
                         └──────────┬──────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      ┌───────────────┐    ┌────────────────┐    ┌────────────────┐
      │ VectorStore   │    │ DocStore (KV)  │    │ IndexStore     │
      │ 向量+原文+元数据│    │ node_id→Node   │    │ index_id→索引结构│
      └───────┬───────┘    └───────┬────────┘    └───────┬────────┘
              │                    │                     │
              ▼                    ▼                     ▼
        Qdrant/pgvector...   Redis/PG/本地json    本地json/PG
```

| Store | 存什么 | 不存会怎样 | 生产建议 |
| --- | --- | --- | --- |
| **VectorStore** | 向量 + node 文本（多数后端存）+ metadata | 没法检索 | 必须外部化 |
| **DocStore**（`BaseDocumentStore`） | `node_id → Node` 全量映射，以及 `ref_doc_id → node_id 列表` | 无法删除单文档、无法去重、`AutoMergingRetriever` 失效、引用无法回溯 | 必须外部化（Redis / PG） |
| **IndexStore** | `index_id → index_struct` | 多索引组合/持久化恢复困难 | 本地 `persist` 即可 |
| **PropertyGraphStore** | 实体-关系三元组 | 仅图谱应用需要 | 按需 |

关键点：**DocStore 不是可有可无的缓存**。`IngestionPipeline` 的去重与 upsert 判断、`delete_ref_doc()` 的反向查找、句子窗口/父子块替换，都依赖它。尤其 `DocstoreStrategy.UPSERTS_AND_DELETE` 策略，没有 docstore 直接抛错。

### 2.1.2 StorageContext：把四者绑在一起

`StorageContext` 是一个把各 Store 组合起来的容器，真正被索引消费的是它：

```python
from llama_index.core import StorageContext, VectorStoreIndex
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.vector_stores.qdrant import QdrantVectorStore

vector_store = QdrantVectorStore(client=qdrant_client, collection_name="docs_v3")
docstore = SimpleDocumentStore()

storage_context = StorageContext.from_defaults(
    vector_store=vector_store,
    docstore=docstore,
)

index = VectorStoreIndex.from_documents(
    documents,
    storage_context=storage_context,
    show_progress=True,
)
```

注意：`from_documents()` 会**同时**往 vector_store 和 docstore 写。如果只想往向量库写（例如你用业务库自己管理原文），就没必要配置 docstore——但那样你得自己保证删除和更新的正确性。

### 2.1.3 一个判断标准

问自己一句话：**「删掉一个源文件时，我知道该删哪些向量吗？」**

- 答不上来 → 你没有 docstore，或者 doc_id 不稳定。这是本章 2.8 要解决的问题。
- 答得上来 → 你的存储分层是对的。

## 2.2 向量库选型：Chroma / Qdrant / Milvus / pgvector

先说结论，再说理由。

### 2.2.1 决策表

| 维度 | Chroma | Qdrant | Milvus | pgvector |
| --- | --- | --- | --- | --- |
| 定位 | 原型 / 小规模 | 中大规模、强过滤 | 超大规模、分布式 | 已有 PG、要事务一致 |
| 部署 | 单进程 / 嵌入式 | Rust 单二进制或云 | 独立集群（standalone 或分布式） | PG 扩展 |
| 实用规模上限 | 百万级（受单机内存限制） | 千万~亿级（分片+量化） | 亿~十亿级 | 千万级（HNSW 常驻内存） |
| 原生混合检索 | ❌ 无 | ✅ sparse+dense（Query API fusion） | ✅ 2.4+ 支持 sparse vector | ⚠️ 靠 `tsvector` 拼 SQL |
| 元数据过滤 | where 语法，无独立索引 | payload + payload index，强 | 标量字段过滤表达式 | SQL 语句，最灵活 |
| 量化/压缩 | ❌ | ✅ scalar/binary/product | ✅ SQ8/PQ/DiskANN | 半精度 vector / 部分索引 |
| 事务/一致性 | 弱 | 弱 | 弱 | ✅ 与业务表同事务 |
| 运维成本 | 极低 | 低 | 高（etcd/对象存储/协调组件） | 最低（复用现有 PG） |
| LlamaIndex 适配成熟度 | 高 | 高 | 中高 | 高 |

经验法则，按顺序判断：

1. **数据量 < 100 万块 且 团队没有 DBA** → Chroma（本地）/ Qdrant（单机 Docker）。
2. **需要和业务数据同库、需要事务、需要 join 权限表** → pgvector。这条经常被低估：多租户的权限过滤用 SQL 写是最省事的。
3. **> 5000 万块 或 要求水平扩展 / 多副本** → Milvus 或 Qdrant 集群。
4. **强过滤（例如 90% 查询都带租户 + 时间范围）** → Qdrant 或 pgvector，不要用 Chroma。

反例：见过不少项目用 Milvus 存 20 万块文档，为了一个 3 节点的集群配了 etcd、MinIO、Pulsar，最后运维成本压垮团队。规模不够就别上分布式。

### 2.2.2 Chroma：原型最快，生产最坑

```python
import chromadb
from llama_index.vector_stores.chroma import ChromaVectorStore
from llama_index.core import StorageContext, VectorStoreIndex

client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="docs_v1",
    metadata={"hnsw:space": "cosine"},   # ← 必须显式指定，默认是 l2
)
vector_store = ChromaVectorStore(chroma_collection=collection)

storage_context = StorageContext.from_defaults(vector_store=vector_store)
index = VectorStoreIndex.from_documents(documents, storage_context=storage_context)
```

四个必须知道的坑：

1. **默认距离是 L2**。不设 `hnsw:space: cosine`，归一化向量的排序结果会和 cosine 有偏差，`similarity_score` 的语义也变了。collection 建好之后改不了，只能重建。
2. **metadata 只支持标量**。`{"tags": ["a", "b"]}` 会抛 `ValueError`。列表字段要先序列化成字符串（`tags:"a,b"`），过滤时用 `$contains` 或干脆拆成多个布尔字段。日期统一存 ISO 字符串或 Unix 时间戳数字，不要存 `datetime` 对象。
3. **别让它自己算 embedding**。Chroma 的 collection 自带 `embedding_function` 默认值（all-MiniLM-L6-v2）。如果你在 LlamaIndex 侧已经算了 embedding，必须确保传给 `get_or_create_collection` 的 collection 没有开启默认函数，否则会重复计算甚至维度冲突。
4. **没有原生混合检索、没有 payload 索引**。过滤是暴力扫 metadata 段，几百万条以上会明显拖慢。

Chroma 0.4 → 0.5 → 0.6 之间客户端 API 改过（`chromadb.Client(Settings(...))` 弃用为 `PersistentClient` / `HttpClient`），锁定版本写进依赖。

### 2.2.3 Qdrant：过滤与混合检索最强

```python
from qdrant_client import QdrantClient, AsyncQdrantClient
from llama_index.vector_stores.qdrant import QdrantVectorStore

client = QdrantClient(url="http://localhost:6333", api_key=None)
aclient = AsyncQdrantClient(url="http://localhost:6333")   # 异步路径需要单独传

vector_store = QdrantVectorStore(
    client=client,
    aclient=aclient,
    collection_name="docs_v1",
    enable_hybrid=True,          # 需要 fastembed 生成 sparse 向量
    batch_size=64,
)
```

Qdrant 的优势是**过滤走 payload index、不是后置扫描**。建 collection 之后要显式建索引，否则过滤退化成全量扫描：

```python
for field, schema in [
    ("tenant_id", "keyword"),
    ("doc_type", "keyword"),
    ("created_at", "integer"),
]:
    client.create_payload_index(
        collection_name="docs_v1",
        field_name=field,
        field_schema=schema,
    )
```

要点：

- `enable_hybrid=True` 会让存储层同时维护 dense 向量和 sparse（BM25 类）向量，检索时用 Qdrant Query API 的 prefetch + fusion 在**服务端**完成融合，省掉一次网络往返和应用层拼接。具体融合函数参数（RRF / DBSF）请对照当前版本的 `QdrantVectorStore` 签名核实。
- 需要 `pip install fastembed`。首次使用会下载 sparse 模型权重。
- 异步场景必须传 `aclient`，只传 `client` 时 `ainsert` / `aquery` 会退化成同步阻塞（在 asyncio 里会卡住事件循环，这个坑很难发现）。
- Qdrant 的 score 语义取决于 `distance` 配置；COSINE 下 LlamaIndex 会做转换，但用原生 SDK 直接查时拿到的是 distance，不是 similarity。两套代码混用时注意方向相反。
- 中等规模（千万级）可以开标量量化把内存压到 1/4：`quantization_config=ScalarQuantization(scalar=ScalarQuantizationConfig(type="int8", always_ram=True))`。召回的轻微损失通常可接受，配合 rerank 能补回来。

### 2.2.4 Milvus：规模够大才值得

```python
from llama_index.vector_stores.milvus import MilvusVectorStore

vector_store = MilvusVectorStore(
    uri="http://localhost:19530",
    token="root:Milvus",
    collection_name="docs_v1",
    dim=1024,
    similarity_metric="COSINE",
    overwrite=False,        # ← 生产环境务必 False，True 会 drop collection
    enable_sparse=False,
)
```

要点：

- `dim` 必须和 embedding 输出维度严格一致，不一致时插入报错但错误信息不直观（表现为 dimension mismatch）。换 embedding 模型 = 换 collection。
- `overwrite=True` 是**删表重建**。这一点在 demo 里很方便，在生产里是事故源。建议把它写死在代码里而非配置项。
- metadata 以 JSON 字段存储，过滤表达式形如 `metadata["tenant_id"] == "t1"`（具体语法随 Milvus 版本演进，需对照官方文档核实）。大数据量下建议把高频过滤字段提成独立的标量字段而不是塞 JSON。
- 亿级规模的关键在索引选型：HNSW 全内存快但贵，`DISKANN` 把图放磁盘省内存，`IVF_PQ` 压缩率高但召回下降明显。这三者的取舍要拿真实数据压测，不能看 benchmark。
- standalone 模式（单容器）够用到千万级，别为了「以后会涨」提前上分布式。

### 2.2.5 pgvector：被低估的默认选项

如果你已经有 PostgreSQL，**默认应该先试 pgvector**，除非规模确实压不住。理由：与业务表同事务（插入文档和插入向量要么都成功要么都回滚）、权限过滤直接写 SQL JOIN、备份/监控/告警全套复用。

```python
from llama_index.vector_stores.postgres import PGVectorStore

vector_store = PGVectorStore.from_params(
    database="app",
    host="localhost",
    password="***",
    port=5432,
    user="app",
    table_name="llama_docs",        # 实际表名会加前缀，见下文
    embed_dim=1024,
    hybrid_search=True,             # 额外建 tsvector 列 + GIN 索引
    text_search_config="simple",    # 中文分词需装 zhparser/pg_jieba，见下
    perform_setup=True,             # 自动建表建扩展，生产建议关掉改手工迁移
)
```

必须自己补的索引（`perform_setup` 未必建全，且建表语句受版本影响，需对照当前版本核实实际表名/列名）：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- HNSW：查询快、建索引慢、吃内存。m=16/ef_construction=64 是通用起点
CREATE INDEX IF NOT EXISTS idx_llama_hnsw
  ON data_llama_docs USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- metadata 是 JSONB，过滤字段建 GIN 或表达式索引
CREATE INDEX IF NOT EXISTS idx_llama_meta
  ON data_llama_docs USING gin (metadata jsonb_path_ops);

-- 高频单字段过滤，表达式 btree 比 GIN 更小更快
CREATE INDEX IF NOT EXISTS idx_llama_tenant
  ON data_llama_docs ((metadata->>'tenant_id'));
```

pgvector 的四个坑：

1. **过滤 + HNSW 的召回塌陷**。`WHERE tenant_id = 't1' ORDER BY embedding <=> $1 LIMIT 10` 时，PG 可能先取 10 个最近邻再过滤，结果不足 10 条甚至 0 条。pgvector 0.8+ 提供 iterative index scan（`SET hnsw.iterative_scan = relaxed_order`）缓解，但仍需实测。更稳的做法是分区表按租户切分，或把 `hnsw.ef_search` 调大。
2. **`ef_search` 默认 40**，召回不够时先调这个（100~200），而不是急着换库。
3. **建索引要吃 `maintenance_work_mem`**，百万级向量建议临时调到 1~2GB，否则 HNSW 构建会退化成磁盘排序，耗时差一个数量级。
4. **中文全文检索需要额外扩展**。`to_tsvector('simple', ...)` 不切词，中文等于按字符切；要正确的中文 BM25 需要 zhparser 或 pg_jieba，并在建索引时用对应配置名。混合检索效果好不好，一半取决于这一步。

### 2.2.6 选型时真正该问的五个问题

1. 向量总量 12 个月后会是多少？（用当前 doc 数 × 平均 chunk 数 × 1.5 估）
2. 查询里带过滤条件的比例是多少？过滤字段基数多大？
3. 是否需要「删除单个用户的全部数据」（GDPR / 客户注销）？—— 这是排除 Chroma 的常见原因。
4. 团队有没有人能值班维护分布式系统？
5. 能不能接受「换 embedding 模型 = 全量重建索引」？这决定了你敢不敢用新模型。

## 2.3 Embedding 模型取舍

### 2.3.1 三个维度在打架：效果、成本、内存

选 embedding 模型不是比 MTEB 分数。真实的约束是三条：

**内存**。HNSW 是常驻内存结构，估算公式：

```
单向量字节数 ≈ d × 4            （float32）
             + M × 2 × 4        （HNSW 每层邻居指针，M 默认 16 → 128 B）

100 万块 × 1024 维 × float32
  = 100万 × (4096 + 128) ≈ 4.0 GB
100 万块 × 1536 维 × float32
  = 100万 × (6144 + 128) ≈ 6.0 GB
100 万块 × 3072 维 × float32
  = 100万 × (12288 + 128) ≈ 11.8 GB
```

再乘上副本数和 `ef_construction` 构建时的临时内存，3072 维在千万级规模下基本不可行。**维度是硬成本，且不可逆**（换了就要重建索引）。

**质量**。MTEB 榜首模型和中等模型在「短查询 → 短段落」上的差距通常只有几个点，但在**领域术语**和**中文长句**上差距可能被放大。榜单和你的数据分布经常不是一回事，务必用 50~100 条真实 query 自建评测集。

**成本**。embedding 单价便宜但量大：一份 1GB 的中文语料 ≈ 3~5 亿 token，用 $0.02/1M 的模型约 $6~10，用 $0.13/1M 的约 $40~65。看起来不多，但**每次改 chunk 策略都要重跑一遍**，迭代十次就是十倍。这是自托管 embedding 的现实价值。

### 2.3.2 主流模型对照（价格为 2025 年公开价，随时会变，需核实）

| 模型 | 维度 | 上下文 | 多语言/中文 | 单价 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `text-embedding-3-small` | 1536（可截断） | 8191 | 中文可用不惊艳 | ~$0.02/1M tok | 英文为主、想省事的起点 |
| `text-embedding-3-large` | 3072（可截断） | 8191 | 中文明显更好 | ~$0.13/1M tok | 质量优先、规模可控 |
| `BAAI/bge-m3` | 1024 | 8192 | ✅ 强，中英混优 | 自托管 | **中文项目的默认推荐** |
| `BAAI/bge-large-zh-v1.5` | 1024 | 512 | ✅ 中文专用 | 自托管 | 纯中文、块较短 |
| `intfloat/multilingual-e5-large` | 1024 | 512 | ✅ | 自托管 | 多语言基线 |
| `jina-embeddings-v3` | 1024（可截断） | 8192 | ✅ | 按量 | 需要多任务 LoRA 时 |
| `voyage-3` / `voyage-3-large` | 1024 / 2048 | 32k | ✅ | 约 $0.06 / $0.18 per 1M | 长文档、质量敏感 |
| `Cohere embed-multilingual-v3` | 1024 | 512 | ✅ | 约 $0.10/1M | 已用 Cohere 生态 |
| `Qwen3-Embedding-0.6B/4B/8B` | 1024/2560/4096 | 32k | ✅ 中文很强 | 自托管 | 有 GPU 且追最新（需核实当前版本支持度） |

几条实践结论：

- **中文为主就选自托管 bge-m3**。1024 维、8192 上下文、中文强、免费、还能同时输出 sparse 向量（配合 Qdrant/Milvus 的混合检索，一份模型干两件事）。
- **别信「维度越高越好」**。bge-m3（1024）在很多中文任务上打得过 3072 维的商业模型，而内存只花 1/3。
- **同一索引里绝不允许混用模型**。两个模型即使同维度，向量空间也不兼容，混存的结果是查询结果随机性变差且难以定位。要换模型，建新 collection（`docs_v2`），双写一段时间后切流。

### 2.3.3 Matryoshka 截断：一条省内存的后路

`text-embedding-3-*`、`jina-v3`、`Qwen3-Embedding` 等支持 MRL（Matryoshka Representation Learning）：把前 N 维截出来再做 L2 归一化，仍然可用。

```python
from llama_index.embeddings.openai import OpenAIEmbedding

embed_model = OpenAIEmbedding(
    model="text-embedding-3-large",
    dimensions=1024,        # 服务端直接返回 1024 维，比本地截断更省带宽
)
```

本地模型要手工截断 + 归一化：

```python
import numpy as np

def truncate_normalize(vec: list[float], dim: int = 512) -> list[float]:
    v = np.asarray(vec[:dim], dtype=np.float32)
    n = np.linalg.norm(v)
    return (v / (n if n else 1.0)).tolist()
```

经验值：3-large 截到 1024 维大约损失 1~3% 效果，换 3 倍内存，通常划算。截到 256 维损失明显，只适合粗筛。

### 2.3.4 归一化与相似度度量必须对齐

这条错了很隐蔽，因为结果「看起来还行」但排序在边缘处是乱的：

- 向量已 L2 归一化 → cosine 与 dot 等价，用哪个都行。
- 向量未归一化 → **必须用 cosine**；用 dot product 会让长文本（向量模长大）系统性占优。
- 用 Euclidean/L2 → LlamaIndex 返回的是 distance，similarity 转换方向要确认，别让阈值过滤写反。

bge 系列、OpenAI 系列默认输出已归一化，但你自己拼的 pipeline（例如加权融合多个模型）之后一定要重新归一化。

### 2.3.5 批处理与缓存：把 embedding 成本压到 1/5

```python
from llama_index.core import Settings

Settings.embed_batch_size = 100   # 本地模型按显存调；OpenAI 受速率限制约 2048
```

三层缓存，从便宜到贵：

1. **节点级缓存**：`IngestionPipeline` 的 `IngestionCache`，基于节点内容哈希，重复文档直接跳过（见 2.8）。
2. **请求级缓存**：embedding 服务前面挂一层 Redis，key = sha256(模型名 + 文本)。同一段文本在「查询期」和「入库期」各算一次的情况很常见，这层能省掉一半查询侧开销。
3. **模型级批处理**：自托管模型务必用 GPU + 动态 batch，单纯逐条调用 QPS 差 10 倍以上。

本地模型配置示例（注意 `device` 和 `max_length`）：

```python
from llama_index.embeddings.huggingface import HuggingFaceEmbedding

embed_model = HuggingFaceEmbedding(
    model_name="BAAI/bge-m3",
    device="cuda",
    max_length=1024,          # 别用 8192，长上下文下显存和耗时会爆
    embed_batch_size=32,
    normalize=True,
)
Settings.embed_model = embed_model
```

`max_length` 是个高频踩坑点：模型支持 8192 不代表你该用 8192。检索用的块一般 256~1024 token，把 `max_length` 设成实际块长能省 4~8 倍时间。

## 2.4 Chunk 策略：决定召回上限的一步

### 2.4.1 先想清楚「检索单元」是什么

切块不是在切文本，是在定义「一个可以被独立召回的语义单元」。所以先问：

- 用户的问题通常需要**多少上下文**才能回答？一段话（300 token）还是一整节（2000 token）？
- 答案是否**跨块**？例如「对比 A 和 B 两个方案」需要两块同时命中。
- 块**单独拿出来**是否可读？「如上所述，该参数默认值为 16」——脱离了上一段的块是垃圾。

这三点决定 chunk_size 的起点：

| 场景 | chunk_size | overlap | 说明 |
| --- | --- | --- | --- |
| FAQ / 客服问答 | 256~384 | 20~50 | 一问一答天然短，块大反而稀释 |
| 技术文档 / 手册 | 512~768 | 50~100 | 默认区间，配合标题 metadata |
| 法律合同 / 论文 | 1024~1536 | 150~250 | 条款和论证需要完整上下文 |
| 代码 | 按函数切 | 0 | 用 `CodeSplitter`，别用句子切分 |
| 表格 / 财报 | 整表 + 行级摘要 | — | 单独处理，见 2.4.5 |

注意 `chunk_size` 的单位是 **token 不是字符**。中文里 1 token ≈ 0.6~1.5 个汉字（取决于 tokenizer），512 token 大约 400~700 汉字。别拿字符数拍脑袋。

### 2.4.2 五种切分器，什么时候用哪个

```python
from llama_index.core.node_parser import (
    SentenceSplitter,
    TokenTextSplitter,
    SemanticSplitterNodeParser,
    HierarchicalNodeParser,
    MarkdownNodeParser,
    CodeSplitter,
)
```

> 补充：`TokenTextSplitter` 是纯按 token 数硬切的兜底实现，不做任何句子/段落边界判断，只在你完全不在乎断句时用（例如结构混乱的 OCR 文本）。绝大多数场景它不如 `SentenceSplitter`。

**1) `SentenceSplitter`（默认，先用它）**

```python
Settings.node_parser = SentenceSplitter(
    chunk_size=512,
    chunk_overlap=64,
    paragraph_separator="\n\n\n",
    secondary_chunking_regex="[^,.;。？！]+[,.;。？！]?",
)
```

它按「段落 → 句子 → 分句」的优先级递归切，保证尽量不断句。默认 `chunk_size=1024, chunk_overlap=200`，对多数场景偏大，建议往 512/64 调。

**2) `SemanticSplitterNodeParser`（语义切分，慎用）**

```python
parser = SemanticSplitterNodeParser(
    buffer_size=1,
    breakpoint_percentile_threshold=95,
    embed_model=embed_model,
)
```

它逐句算 embedding，在相邻句相似度骤降处断开。优点是不受固定长度约束；缺点是 **ingestion 阶段要为每一句话算一次 embedding**，成本 3~5 倍、速度慢一个数量级，而且**切出来的块长度方差极大**（有的 50 token，有的 2000 token），给后续检索带来麻烦。

结论：只在文档结构混乱、段落本身没有意义时用，并且必须在离线评测里证明它比 SentenceSplitter 好。大多数项目不需要它。

**3) `HierarchicalNodeParser` + `AutoMergingRetriever`（解决 chunk_size 两难）**

```python
from llama_index.core.node_parser import HierarchicalNodeParser, get_leaf_nodes
from llama_index.core.retrievers import AutoMergingRetriever
from llama_index.core.storage.docstore import SimpleDocumentStore

parser = HierarchicalNodeParser.from_defaults(chunk_sizes=[2048, 512, 128])
nodes = parser.get_nodes_from_documents(documents)
leaf_nodes = get_leaf_nodes(nodes)   # 只有叶子节点进向量库

docstore = SimpleDocumentStore()
docstore.add_nodes(nodes)           # ← 父节点必须进 docstore！
```

原理：用小块（128）做检索保证精度，命中后如果同一父块（512/2048）下的兄弟块命中比例超过 `simple_ratio_thresh`（默认 0.4），就自动把父块整块交给 LLM。**这是唯一不牺牲召回精度的「大块策略」**。

代价：docstore 必须存全部层级节点，存储翻倍；检索多一次 docstore 查询。

**4) `MarkdownNodeParser`（有结构的文档必用）**

```python
parser = MarkdownNodeParser()
```

按 `#`/`##` 标题层级切，并把标题路径写进 metadata（`header_path`）。这对技术文档几乎是免费的召回提升——「第 3 节 / 3.2 配置项」这样的上下文让 LLM 知道自己在读什么。

配套 `MarkdownElementNodeParser` 能把表格/代码块单独抽成结构化节点（依赖 `unstructured`），适合报表类文档，但更重、更脆，先用简单的那个。

**5) `CodeSplitter`（按语法切）**

```python
parser = CodeSplitter(
    language="python",
    chunk_lines=40,
    chunk_lines_overlap=15,
    max_chars=1500,
)
```

依赖 `tree_sitter` 的对应语言包。代码块的关键是**保留函数签名和所属类名**，建议切完后手工在块头部注入 `file_path + class + def`，否则「这个函数在哪」这类问题永远检索不到。

### 2.4.3 怎么用数据决定 chunk_size，而不是靠感觉

一个有结论的方法（半天能跑完）：

1. 从真实日志里挑 50~100 条 query，**每条标注它对应的原文片段**（正确答案所在位置）。
2. 用 3 组参数（例如 256/512/1024，overlap 固定 15%）各建一个 collection。
3. 对每条 query 取 top-10，算 **HitRate@10** 和 **MRR**：目标块是否出现、排第几。
4. 关键指标是**「召回但排序靠后」的比例**。如果 256 的 HitRate 高但 MRR 低，说明块太小、语义不完整——这时上 rerank 或 Hierarchical 合并，而不是加 chunk_size。

一个常见现象：**chunk_size 从 512 加到 1024，HitRate@10 涨了 3 个点，但最终答案质量没变甚至变差**（因为混入了无关内容）。这说明瓶颈不在召回而在精度，该上 rerank 了（2.7）。

### 2.4.4 metadata 设计：切块时顺手做的事，检索时省一周

切块时能拿到的元数据，比你以为的多。趁 `node.metadata.update(...)` 便宜，一次写全：

```python
from llama_index.core.schema import MetadataMode

def enrich(node, doc):
    node.metadata.update({
        "doc_id":       doc.doc_id,
        "source":       doc.metadata.get("file_path"),
        "tenant_id":    doc.metadata.get("tenant_id"),
        "doc_type":     doc.metadata.get("doc_type"),
        "lang":         doc.metadata.get("lang"),
        "created_at":   doc.metadata.get("created_at"),      # ISO 字符串或 int
        "section":      node.metadata.get("header_path", ""),
        "chunk_index":  node.metadata.get("chunk_idx"),
    })
    return node
```

两个细节：

- `MetadataMode`：块内容送给 LLM 时可以带上部分 metadata（`node.get_content(metadata_mode=MetadataMode.LLM)`），但**不要把整个 metadata 塞进 embedding 文本**——会让向量被「tenant_id=t_001」这种无信息内容污染。只在 LLM 侧注入。
- 数值字段存数字、时间存 ISO 字符串或 Unix 整数。过滤器里的类型不匹配（字符串 "2025" vs 数字 2025）在各后端表现不一致，且报错信息很差。

### 2.4.5 表格与图片：不要硬切

表格被 `SentenceSplitter` 切碎后，每块都是「没有表头的数字」，检索到也没用。三种处理：

1. **整表作为一个节点**（表小于 ~2000 token 时），metadata 里存表名和所在章节。
2. **行级展开**：每行 = 表头拼上该行，生成 N 个小节点。召回精准，但会丢跨行汇总语义。
3. **LLM 生成摘要 + 保留原表**：索引摘要（便宜、可检索），LLM 生成阶段取原表。这个组合效果最好，代价是多一次预计算。

图片走多模态 embedding 或先做图注（caption）再纯文本索引。别指望文本 embedding 模型理解图片。

## 2.5 Metadata Filter：最被低估的性能杠杆

### 2.5.1 API 用法

```python
from llama_index.core.vector_stores import (
    MetadataFilters,
    MetadataFilter,
    FilterOperator,
    FilterCondition,
)

filters = MetadataFilters(
    filters=[
        MetadataFilter(key="tenant_id", value="t_001"),
        MetadataFilter(key="doc_type", value="manual"),
        MetadataFilter(key="created_at", value=1735689600, operator=FilterOperator.GTE),
    ],
    condition=FilterCondition.AND,     # 默认 AND
)

retriever = index.as_retriever(
    similarity_top_k=20,
    filters=filters,
)
```

常用 `FilterOperator`：`EQ` / `NE` / `GT` / `GTE` / `LT` / `LTE` / `IN` / `NIN` / `TEXT_MATCH` / `CONTAINS`。**支持度因后端而异**，`TEXT_MATCH` 和 `CONTAINS` 在 Chroma / pgvector 上行为不一致，用前先小样本验证。

### 2.5.2 后端翻译与索引要求（这是性能关键）

| 后端 | 翻译成 | 不加索引的后果 |
| --- | --- | --- |
| Chroma | `where` 字典 | 无索引，全量扫 metadata |
| Qdrant | `payload filter` | 过滤阶段全扫，召回数为 0 或极慢 |
| Milvus | 布尔表达式 | 标量字段无索引则退化为暴力 |
| pgvector | SQL `WHERE metadata->>'k' = 'v'` | 无索引即顺序扫描整表 |
| SimpleVectorStore | Python 内存过滤 | 仅适合 < 1 万条 |

**Qdrant 必须建 payload index**（见 2.2.3），**pgvector 必须建表达式索引或 GIN**（见 2.2.5）。这一步不做，过滤就是性能黑洞：1000 万条数据下，一个未索引的 `tenant_id` 过滤能让查询从 20ms 变成 3s。

### 2.5.3 过滤选择性决定策略

关键概念：**过滤后剩多少**。

- 过滤后剩 > 10%（例如按 doc_type 过滤，有 3 种类型）→ 先过滤再向量检索，几乎无损。
- 过滤后剩 < 1%（例如按 tenant_id，几千个租户）→ HNSW 的图遍历会被打散，**召回严重塌陷**。这是 pgvector/Qdrant 的通病。

对策，按优先级：

1. **物理隔离**：租户数量少就一租户一 collection / 一分区表。这是唯一彻底解法。
2. **分区键**：pgvector 用 `PARTITION BY HASH (tenant_id)`，每个分区独立 HNSW。
3. **扩大候选集**：`similarity_top_k` 从 10 提到 50~100，再在应用层截断。代价是 LLM 侧 token 和 rerank 成本上升。
4. **调整搜索参数**：pgvector 的 `hnsw.ef_search`、Qdrant 的 `hnsw_ef`，调大换召回。

### 2.5.4 一个必须避免的反模式：把权限写进 prompt

```python
# ❌ 错：检索完再让模型「不要回答无权内容」
retrieved = retriever.retrieve(query)
prompt = "以下是资料，如果资料不属于用户 t_001 请忽略：..."
```

这既漏数据（敏感内容已经进了上下文，日志/缓存里都有）又不可靠（模型不一定听）。**权限必须在检索层过滤**，用 `MetadataFilters` 或 SQL JOIN 权限表。

## 2.6 Hybrid Search：向量检索不是万能的

### 2.6.1 向量检索在哪类查询上会失效

这不是玄学，是有明确规律的。dense 检索擅长「意思相近」，不擅长「精确匹配」：

| 查询类型 | 例子 | dense 表现 | 关键词检索表现 |
| --- | --- | --- | --- |
| 专有名词 / 型号 | 「XR-7840 的额定电压」 | 差（稀有 token 在训练分布外） | ✅ 极好 |
| 错误码 / 编号 | 「错误 E5021 怎么解决」 | 差 | ✅ 极好 |
| 代码标识符 | 「`configure_retries()` 默认参数」 | 差 | ✅ 好 |
| 同义改写 | 「怎么退货」 vs 「退款流程」 | ✅ 好 | 差 |
| 长描述性问题 | 「多租户场景下如何隔离向量索引」 | ✅ 好 | 中 |
| 否定/限定 | 「不含电池的版本」 | 中 | 中 |

实际业务里前三种占比常常超过 30%，所以**混合检索基本是生产标配**，不是可选优化。

### 2.6.2 三条实现路径

**路径 A：后端原生融合（首选）**

Qdrant（`enable_hybrid=True`）和 Milvus（2.4+，`enable_sparse=True`）能在服务端一次请求内完成 dense + sparse 两路召回并融合。优点：一次网络往返、延迟低、无需在应用层维护 BM25 索引。

```python
# Qdrant 原生混合检索（参数名随版本演进，需对照官方文档核实 fusion 配置项）
from llama_index.vector_stores.qdrant import QdrantVectorStore

vector_store = QdrantVectorStore(
    client=client,
    aclient=aclient,
    collection_name="docs_hybrid",
    enable_hybrid=True,
)
index = VectorStoreIndex.from_vector_store(vector_store)
retriever = index.as_retriever(similarity_top_k=20)
```

前提是入库时同时写了 sparse 向量。如果你已经用 bge-m3 建了 dense 索引，需要**重新入库**才能启用（sparse 向量是入库时生成的）。

**路径 B：应用层 BM25 + QueryFusionRetriever（通用，Chroma/pgvector 只能这样）**

```python
from llama_index.retrievers.bm25 import BM25Retriever
from llama_index.core.retrievers import QueryFusionRetriever
from llama_index.core import VectorStoreIndex

# BM25 需要全部节点在内存里建倒排索引
bm25 = BM25Retriever.from_defaults(
    nodes=all_nodes,            # 或 docstore.docs.values()
    similarity_top_k=20,
    language="zh",              # 中文分词依赖 jieba，需核实当前版本参数
)

vector_retriever = index.as_retriever(similarity_top_k=20)

hybrid = QueryFusionRetriever(
    [vector_retriever, bm25],
    similarity_top_k=10,
    num_queries=1,              # 1 = 不做 query 扩展，只融合
    mode="reciprocal_rerank",   # 或 "relative_score" / "dist_based_score" / "simple"
    use_async=True,
    llm=Settings.llm,           # num_queries>1 时会用它改写查询
)
```

三个必须注意的点：

1. **`num_queries=1`**。默认是 4，会调用 LLM 把一条 query 改写成 4 条并行检索。它有增益但会**多一次 LLM 调用（+300~800ms）**，多数场景不划算，除非你在做 recall 极限优化。
2. **BM25 索引在内存里**。100 万块文本的文件大约占 1~3 GB RSS，且**数据更新后必须重建**。更新频繁的场景考虑换路径 A 或 C，或者按业务分片、只对热数据建 BM25。
3. **中文必须分词**。默认英文分词器会把整段中文当一个 token，BM25 完全失效（表现为混合检索和纯向量检索效果一样）。要么用 `language="zh"`（内部走 jieba），要么自己传入预分词的 tokenizer。

**路径 C：自己算分数融合（最可控）**

当后端和框架的融合逻辑不满足需求（例如要按字段加权、要做时间衰减、要保证某些块必进），就直接拿两路 top-k 自己打分：

```python
def rrf_fuse(result_lists, k=8, weights=None):
    """Reciprocal Rank Fusion，只用排名不用分数，见 2.6.3"""
    weights = weights or [1.0] * len(result_lists)
    scores = {}
    picked = {}
    for w, results in zip(weights, result_lists):
        for rank, nws in enumerate(results, start=1):
            nid = nws.node.node_id
            scores[nid] = scores.get(nid, 0.0) + w / (k + rank)
            picked.setdefault(nid, nws.node)
    ordered = sorted(scores.items(), key=lambda x: -x[1])
    return [(picked[nid], s) for nid, s in ordered]
```

### 2.6.3 RRF 为什么比「分数加权」稳

Reciprocal Rank Fusion 的公式：

```
score(d) = Σ_r  w_r / (k + rank_r(d))      k 通常取 60
```

关键洞察：**它只用排名，不用分数**。因为 dense 的 cosine 相似度和 BM25 的分数**量纲完全不同、分布也不同**（BM25 可以到 20+，cosine 在 0~1），直接相加等于让 BM25 单方面决定结果。

`relative_score` 模式会先把两路分数各自归一化到 [0,1] 再相加，比朴素相加好，但对**单路只有 1 个结果**的极端情况会失真。`dist_based_score` 用距离的分布做归一化，抗噪更好。经验上：

- 数据量大、两路质量都不错 → RRF（`reciprocal_rerank`）。
- 某一方明显更可靠 → `relative_score` 并给权重。
- 有 rerank 兜底 → 随便选，融合只是把候选集扩大。

### 2.6.4 融合后的候选集大小

这是最容易调错的地方。记住链条：

```
两路各取 20  →  融合去重后 25~35  →  rerank 后取 5  →  LLM
```

- 每路 `similarity_top_k` 太小（比如 5）→ 融合没意义，两路结果高度重合。
- 融合后直接给 LLM 20 条 → 上下文膨胀、无关内容干扰、成本翻倍。
- **融合的正确出口是 rerank**。没有 rerank 的混合检索，通常还不如纯向量检索，因为关键词召回的噪声被引入了。

## 2.7 Rerank：把精度从 60% 拉到 85% 的那一步

### 2.7.1 它解决什么问题

embedding 是 **query 和 doc 分开编码**（bi-encoder），两者从没见过面，只能靠向量空间「大概对齐」。rerank 模型是 **cross-encoder**，把 query 和 chunk 拼在一起过一遍模型，能捕捉「这个块到底回答了没有」这种细粒度判断。

典型收益（不同数据集差异大，但量级如此）：

| 指标 | 纯向量 top-10 | + rerank top-5 |
| --- | --- | --- |
| 命中率（正确块在候选集内） | 80~90% | 不变（rerank 不提升召回上限） |
| 正确块进入上下文的比例 | 50~65% | 80~90% |
| 最终答案忠实度 | 基线 | 明显提升 |

关键认知：**rerank 不能补救召回失败**。正确块不在候选集里，重排再好也没用。所以顺序永远是「先扩大召回（hybrid + 大 top_k），再重排收窄」。

### 2.7.2 三种实现

**本地 cross-encoder（推荐，中文用 bge-reranker）**

```python
from llama_index.core.postprocessor import SentenceTransformerRerank

reranker = SentenceTransformerRerank(
    model="BAAI/bge-reranker-v2-m3",   # 中英双语，多语言也可用
    top_n=5,
    device="cuda",
)
```

依赖 `sentence-transformers` + torch。v2-m3 是 568M 参数，GPU 上 50 个块约 100~200ms，CPU 上会到 1~3s（不可接受）。

**托管 API（省运维）**

```python
from llama_index.postprocessor.cohere_rerank import CohereRerank

reranker = CohereRerank(model="rerank-v3.5", top_n=5)
```

延迟 80~300ms（含网络），按「查询数 × 文档数 × token」计费。适合不想自建 GPU 的团队。同类还有 voyage rerank、Jina reranker API。

**LLM 重排（最贵最慢，特定场景才用）**

```python
from llama_index.core.postprocessor import LLMRerank

reranker = LLMRerank(top_n=5, choice_batch_size=5)
```

把候选块编号后让 LLM 排序。优点是能理解复杂意图，缺点是 **1~3 秒 + 每块都要 token**，20 个候选就是一次完整的大模型调用。只在你已经在用强模型、且查询量很小时考虑。

### 2.7.3 top_n 与候选数的配比

```python
retriever = index.as_retriever(similarity_top_k=50)   # 召回宽
query_engine = index.as_query_engine(
    similarity_top_k=50,
    node_postprocessors=[reranker],                  # reranker.top_n=5
)
```

经验配比：

| 场景 | 召回 | rerank top_n | 理由 |
| --- | --- | --- | --- |
| 简单问答 | 20~30 | 3~5 | 多了反而干扰 |
| 需要综合多段 | 50 | 6~10 | 覆盖多个方面 |
| 对比/列举类 | 50~80 | 10~15 | 必须多块并存 |
| 摘要素材 | 100 | 15~20 | 保覆盖 |

注意 **rerank 的延迟和候选数近似线性**。50 个候选在 GPU 上约 200ms，CPU 上 5s+。这也是为什么要用 GPU 或者用托管 API。

另一个细节：**块越长 rerank 越慢越不准**。cross-encoder 截断在 512 token 左右，超过的部分被丢掉。所以用 `HierarchicalNodeParser` 的话，rerank 应该作用在**小块**上，合并成父块发生在 rerank 之后。

### 2.7.4 什么情况不该上 rerank

- **候选集本来就很小**（top_k=5）：rerank 提升有限，白加延迟。
- **查询是精确查找类**（「找一下合同编号 X 的附件」）：关键词检索直接命中，rerank 无关。
- **延迟预算极紧**（< 1s 端到端）：那应该优化 embedding 和向量库，而不是加一道 cross-encoder。
- **离线批处理**：不需要，直接上更大的 top_k 给 LLM。

### 2.7.5 阈值过滤：比 top_n 更好用的补充

```python
from llama_index.core.postprocessor import SimilarityPostprocessor

postprocessors = [
    SimilarityPostprocessor(similarity_cutoff=0.45),   # 先砍掉明显不相关的
    reranker,
]
```

作用是：查询本身在库里没有答案时，返回 0 条而不是硬凑 5 条垃圾给 LLM 编。这对「不知道就说不知道」至关重要。

`similarity_cutoff` 的取值必须**在你的数据上实测**，不能抄（不同模型的分数分布完全不同；cosine 0.45 对 bge 是「一般相关」，对 OpenAI 可能是「很相关」）。做法：拿 100 条 query 画出正确块和错误块的分数分布，取分界点。

## 2.8 增量 Ingestion 与去重：生产事故高发区

### 2.8.1 先说结论：去重靠两层机制，缺一不可

| 层 | 机制 | 谁负责 | 防的是什么 |
| --- | --- | --- | --- |
| 第一层 | **内容哈希**（`Document.hash` / 节点缓存 key） | 框架自动 | 同一份内容被重复索引 |
| 第二层 | **稳定 doc_id** | **你** | 同一文件的新版本与旧版本对不上号 |

第一层框架会做，所以「重复跑同一次 ingestion」不会产生重复向量。但第二层必须自己保证，否则会出现一种很难查的现象：**文件更新了，旧内容还留在库里，检索时新旧版本混着返回**。

根因：`Document` 不传 `doc_id` 时，默认是随机 UUID。今天索引 `report.pdf`，明天再索引同一个文件，得到的是两个不同的 doc_id → docstore 认为是两份文档 → 旧向量永远删不掉。

```python
# ❌ 错：每次都是新身份
doc = Document(text=text, metadata={"path": "/data/report.pdf"})

# ✅ 对：身份由业务主键决定，与内容无关
import hashlib

def doc_id_for(tenant: str, path: str) -> str:
    raw = f"{tenant}:{path}".encode("utf-8")
    return "d_" + hashlib.sha256(raw).hexdigest()[:24]

doc = Document(
    text=text,
    doc_id=doc_id_for("t_001", "/data/report.pdf"),
    metadata={"path": "/data/report.pdf", "tenant_id": "t_001"},
)
```

顺带一个好用的兜底：给每个节点也算一个稳定 id（内容 + 位置），让「同一段内容出现在两个文件里」也能被识别：

```python
import hashlib
from llama_index.core.schema import TransformComponent, MetadataMode

class StableNodeId(TransformComponent):
    """基于内容+元数据生成稳定 id，重复 ingestion 时 id 不变"""

    def __call__(self, nodes, **kwargs):
        for n in nodes:
            payload = n.get_content(metadata_mode=MetadataMode.ALL)
            n.id_ = "n_" + hashlib.sha256(payload.encode("utf-8")).hexdigest()[:32]
        return nodes
```

⚠️ 前提是你的 embedding 模型也固定。换了模型而 id 不变，会出现「id 相同但向量语义不同」的静默错乱——所以换模型必须换 collection 名。

### 2.8.2 IngestionPipeline：一次配置，覆盖增删改

```python
from llama_index.core.ingestion import (
    IngestionPipeline,
    IngestionCache,
    DocstoreStrategy,
)
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core.node_parser import SentenceSplitter
from llama_index.vector_stores.qdrant import QdrantVectorStore

docstore = SimpleDocumentStore()
vector_store = QdrantVectorStore(client=client, collection_name="docs_v2")

pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_size=512, chunk_overlap=64),
        StableNodeId(),                    # 自定义：稳定 id
        embed_model,                       # 显式放进 transformations
    ],
    docstore=docstore,
    vector_store=vector_store,
    cache=IngestionCache(),               # 节点级缓存，跳过已处理内容
    docstore_strategy=DocstoreStrategy.UPSERTS,
)

nodes = pipeline.run(
    documents=new_docs,
    num_workers=4,
    show_progress=True,
)
```

关键：**`embed_model` 要显式放进 `transformations`**。只设 `Settings.embed_model` 时，`IngestionPipeline` 在某些版本里不会自动追加 embedding 步骤，导致向量库收到的是空向量或抛错。（这一行为在 0.10~0.12 之间调整过，属「需对照官方文档核实」项，稳妥做法就是显式写进去。）

### 2.8.3 三种 docstore_strategy 的语义

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `DUPLICATES_ONLY` | 只跳过完全重复的文档，不做更新 | 一次性导入、只增不改 |
| `UPSERTS` | 文档内容变化时，插入新节点（旧节点保留） | 需要版本留存的场景 |
| `UPSERTS_AND_DELETE` | 内容变化时**删除旧节点**再插新节点 | **绝大多数生产场景** |

注意 `UPSERTS` 会累积垃圾：同一 doc_id 反复更新，向量库里堆 N 份历史版本，检索时都被召回。除非你确实要做版本对比，否则用 `UPSERTS_AND_DELETE`。

### 2.8.4 删除：三种粒度

```python
# 1) 删单个文档（连带其所有节点）—— 依赖 docstore 的 ref_doc_id 映射
index.delete_ref_doc(doc_id, delete_from_docstore=True)

# 2) 删单个节点
index.delete_nodes([node_id])

# 3) 按条件批量删（租户注销、数据过期）
#    from qdrant_client.models import FilterSelector, Filter, FieldCondition, MatchValue
#    LlamaIndex 的通用接口不支持，直接走后端原生 API：
client.delete(
    collection_name="docs_v2",
    points_selector=FilterSelector(
        filter=Filter(must=[FieldCondition(key="tenant_id", match=MatchValue(value="t_001"))]),
    ),
)
```

第 3 种是**客户注销 / GDPR 删除**的必备能力。选型时如果只能按 id 删（Chroma 早期版本就是这样），批量删除就得先查全量 id 再删，几百万条会把内存打爆——这是排除某个向量库的正当理由。

另外，模糊删除之后一定要**同时清理 docstore**，否则 docstore 里残留 node_id，下次 ingestion 会认为「这个节点已存在」而跳过，形成幽灵状态。

### 2.8.5 断点续跑与容错

大库首次导入（几十万文档）必然中途失败。要点：

```python
# 分批 + 持久化 pipeline 状态
for batch in chunked(documents, 500):
    try:
        pipeline.run(documents=batch, num_workers=8)
    except Exception as e:
        log.error("batch failed: %s", e)
        failed.extend(batch)          # 收集后重试，不要整批回滚
    finally:
        pipeline.persist("./pipeline_store")   # 每批落盘，重启可续
        docstore.persist("./docstore.json")
```

`pipeline.persist()` 保存的是 cache + docstore 状态。恢复：

```python
pipeline = IngestionPipeline.load("./pipeline_store")
```

（`load` 的签名在版本间有调整，若加载失败就手工重建，把 docstore 从 json 读回来再构造——效果一样。）

三个实践细节：

- `num_workers` 对远程 embedding API 是并发数，注意速率限制；对本地 GPU 模型设成 1~2 就够（GPU 本身是批处理的，多进程会抢显存）。
- 失败不要整批重来，因为已经有了 cache，重跑只会跳过成功的部分——但**前提是 cache 落盘了**。
- 大批量导入前先跑 100 条做**维度与字段自查**：维度、metadata 类型、时间字段格式。错了要重来一遍的成本是几小时。

### 2.8.6 多租户的 ingestion 隔离

三条路，按成本从低到高：

1. **共享 collection + tenant_id 过滤**（最省），但要注意 2.5.3 的选择性问题。
2. **一租户一 collection**（几百租户以内可行）。删除即 drop collection，干净利落。
3. **一租户一分区**（pgvector 分区表 / Qdrant 多 collection 分片）。

租户数量超过几千、且强合规要求时，基本只能走 2 或 3。提前算好租户数增长曲线，别等出事再迁。

## 2.9 索引持久化：三种组合与它们的坑

### 2.9.1 组合一：全本地（仅开发/单机）

```python
from llama_index.core import VectorStoreIndex, StorageContext, load_index_from_storage

index = VectorStoreIndex.from_documents(docs)
index.storage_context.persist(persist_dir="./storage")

# 重新加载
storage_context = StorageContext.from_defaults(persist_dir="./storage")
index = load_index_from_storage(storage_context)
```

`persist` 会写几个 json：docstore、index_store、以及 `SimpleVectorStore` 的向量文件（文件名随版本变过，`vector_store.json` → `default_vector_store.json`，需按版本核实）。

⚠️ 别把这个当生产方案：全量向量装在一个 json 里，加载慢、并发差、更新要重写整个文件。只适合 < 几万块的原型和评测。

### 2.9.2 组合二：外部向量库 + 本地 docstore（生产最常用）

```python
from llama_index.core import StorageContext, VectorStoreIndex, load_index_from_storage
from llama_index.vector_stores.qdrant import QdrantVectorStore

# 写入期
vector_store = QdrantVectorStore(client=client, collection_name="docs_v2")
storage_context = StorageContext.from_defaults(vector_store=vector_store)
index = VectorStoreIndex.from_documents(docs, storage_context=storage_context)
index.storage_context.persist(persist_dir="./storage")   # 只落 docstore/index_store

# 读取期（服务重启后）
storage_context = StorageContext.from_defaults(
    vector_store=vector_store,                              # 重新连，不从磁盘读
    persist_dir="./storage",                               # docstore 从这里恢复
)
index = load_index_from_storage(storage_context)
```

这个组合的含义：**向量在数据库里（持久、可查），docstore 在本地 json 里（轻量、但也丢了）**。

问题来了：docstore 丢了怎么办？——删除失效、去重失效、`AutoMergingRetriever` 失效。单机部署可以接受（备份 json 即可），多副本部署就不行了：A 副本和 B 副本的 docstore 会漂移。

### 2.9.3 组合三：全部外部化（多副本生产）

```python
# docstore 换成 Redis 或 Postgres（包名需对照官方文档核实当前集成包）
from llama_index.storage.docstore.redis import RedisDocumentStore

docstore = RedisDocumentStore.from_redis_uri(
    redis_uri="redis://localhost:6379",
    namespace="llama_docstore",
)

storage_context = StorageContext.from_defaults(
    vector_store=vector_store,
    docstore=docstore,
)
```

有了它，任意副本重启都能恢复完整映射，滚动发布不会丢状态。成本是一个 Redis 实例，很值。

### 2.9.4 最常见的四个错误

**错误 1：用 `from_vector_store` 恢复时没传 embed_model**

```python
# ❌ 会用 Settings 默认的模型（通常是 OpenAI 1536 维）去编码 query
index = VectorStoreIndex.from_vector_store(vector_store)

# ✅ 显式指定，和入库时同一模型
index = VectorStoreIndex.from_vector_store(
    vector_store,
    embed_model=embed_model,      # 同一个 bge-m3 / 同一个 dimensions
)
```

症状是「检索能跑但结果莫名其妙」或者 cosine 计算出 NaN/异常值。**维度不同不会报错**（向量库不会校验 query 向量维度和集合维度，某些后端会，某些不会），这是最阴的一类 bug。

**错误 2：重复 persist 导致 docstore 与向量库不一致**

如果中途在别的进程里往向量库写过数据，本地 docstore 是旧的。恢复后 docstore 认为「这些节点不存在」，去重逻辑就会重复插入。对策：**所有写入都走同一个 pipeline 实例**，或者写入后立刻 persist。

**错误 3：加载了旧的 index_store**

`load_index_from_storage` 会读 `index_store.json`。如果你改了 node_parser 参数但沿用旧目录，索引结构和实际数据对不上。**换切分策略 = 换 persist 目录 + 换 collection**。

**错误 4：跨环境拷贝 persist 目录**

本地跑通的 storage 目录拷到服务器，路径、模型、collection 名全变了，能加载但查到的是错的。persist 目录应该是**构建产物**，每次重建，不进 git。

### 2.9.5 一个可用的目录约定

```
storage/
  {collection}/          # docs_v2_1024_bge-m3
    docstore.json
    index_store.json
    pipeline_cache/
```

collection 名里编码三个要素：**数据版本 + 维度 + 模型名**。这样任何一次模型或策略变更，物理上就是新集合，不会互相污染，回滚也只是改一个环境变量。

## 2.10 延迟与成本调优

### 2.10.1 先把延迟拆开，再谈优化

端到端 P95 往往是 4~8 秒，其中 LLM 生成只占一半。一张典型分解表（**经验量级，必须在你的环境实测**）：

| 阶段 | P50 | P95 | 备注 |
| --- | --- | --- | --- |
| query embedding（API） | 80 ms | 200 ms | 网络抖动是主因 |
| query embedding（本地 GPU） | 15 ms | 40 ms | 需预热，首请求慢 10 倍 |
| dense 检索（HNSW，50 万条） | 10 ms | 30 ms | 带过滤会翻倍 |
| dense 检索（pgvector + 未索引过滤） | 200 ms | 2 s | 典型的性能黑洞 |
| BM25（内存，50 万块） | 20 ms | 60 ms | 随数据量线性增长 |
| RRF 融合 | < 5 ms | 15 ms | 纯计算 |
| rerank（GPU，50 候选，512 tok） | 150 ms | 300 ms | CPU 上 ×10 |
| rerank（托管 API） | 250 ms | 600 ms | 含网络 |
| LLM 首 token | 400 ms | 1.2 s | 与 prompt 长度强相关 |
| LLM 生成 500 tok | 4 s | 9 s | 主要成本项 |

读法：**检索链（前 5 行）合计通常 100~400ms，占比不到 10%**。所以：

- 用户抱怨「慢」时，先看 LLM 输出长度和 prompt token 数，而不是急着换向量库。
- 但**过滤没建索引**这一条会让检索链从 100ms 变成 2s，是唯一值得大动干戈的检索侧问题。

### 2.10.2 成本模型：写下来才能优化

```
月成本 = 入库成本（一次性，但要乘以重跑次数）
       + 查询成本 × 月查询量
       + 存储成本（向量内存 + 原文）

查询成本 = embed(query)             # 1 次，极少
         + rerank(cand × avg_chunk_tok)
         + llm(prompt_tok + output_tok)

prompt_tok ≈ top_n × avg_chunk_tok + 系统提示 + 历史对话
```

算例（10 万查询/月，top_n=5，块 512 token，输出 400 token，用中端 LLM）：

```
prompt ≈ 5 × 512 + 300 = 2860 tok
输出   ≈ 400 tok

若 LLM 定价 $0.5/1M 输入、$1.5/1M 输出（示意，按实际模型价换算）：
  单次 ≈ 2860/1e6 × 0.5 + 400/1e6 × 1.5 ≈ $0.002
  月成本 ≈ 10 万 × 0.002 = $200

rerank 若走托管 API（按 1M tokens 计，示意价 $2/1M）：
  单次候选 token ≈ 50 × 512 = 25.6k → $0.05    ← 比 LLM 还贵！
```

第二条是很多人算漏的：**托管 rerank 的候选数 × 块长 会把成本吃掉**。50 个候选 × 512 token = 2.5 万 token/次，接近 LLM prompt token 的 10 倍。

对策：候选从 50 降到 20（延迟和成本各降 60%），或者自建 GPU reranker（边际成本≈0，只看 GPU 租金）。

### 2.10.3 优化清单，按 ROI 从高到低

| # | 措施 | 典型收益 | 代价 |
| --- | --- | --- | --- |
| 1 | **给过滤字段建索引** | 检索 10× 提速 | 一条 DDL |
| 2 | **查询级 answer cache**（Redis，key=规范化 query + 租户 + 索引版本） | 命中率 15~40%，成本直降 | 泄露风险（必须按租户隔离） |
| 3 | **rerank 候选数减半** | 延迟 -50%，rerank 成本 -50% | 需评测确认不掉点 |
| 4 | **块长缩短到 256~384** | prompt token 减半 | 可能丢上下文 |
| 5 | **降维（3072→1024）** | 内存 -66%，检索更快 | 1~3% 效果损失 |
| 6 | **embedding 结果缓存** | 重复文本零成本 | 需要 Redis |
| 7 | **异步 / 流式** | 感知延迟 -60%（首 token 先出） | 改前端 |
| 8 | 换更快的向量库 | 通常 < 50ms | 迁移成本，**优先级最低** |

第 8 条放最后是有原因的：大多数人上来就想换向量库，但检索只占端到端 10%。先把 1、2、3 做完，收益是换库的十倍。

### 2.10.4 必埋的监控指标

```python
import time
from llama_index.core.callbacks import CallbackManager, LlamaDebugHandler

# 开发期用 debug handler 看每阶段耗时
debug = LlamaDebugHandler(print_trace_on_end=True)
Settings.callback_manager = CallbackManager([debug])

# 生产期：自己在 retriever / reranker 外层包一层埋点，字段至少包含：
#   trace_id, query_hash, tenant_id
#   embed_ms, search_ms, rerank_ms, llm_ttft_ms, total_ms
#   candidates_in, candidates_out, top_score, score_gap
#   tokens_prompt, tokens_output, cache_hit
```

其中 **`top_score` 与 `score_gap`（第 1 名与第 5 名的分差）** 特别有用：

- top_score 长期低于阈值 → 库里就没有这些内容，应该去补数据，而不是调 prompt。
- score_gap 极小 → 检索结果模糊，说明块太长太泛或者问题太宽，是上 rerank 的信号。
- 这两个指标画成时间序列，能提前发现「某类文档新导入后召回整体变差」这类回归。

### 2.10.5 压测怎么做才有效

1. 用**真实 query 分布**，不要用随机字符串（embedding 服务的耗时与内容相关）。
2. 分阶段压：只压检索（不含 LLM）→ 只压 embedding → 端到端。否则定位不了瓶颈。
3. 关注 **P95 而不是均值**。向量库的尾延迟（GC、索引重建、连接池耗尽）全在 P95 之后。
4. 并发从 1 逐步加到目标值的 2 倍，画「并发-延迟」曲线，找拐点。拐点通常来自连接池大小或 GPU batch。
5. pgvector 压测时记得连接池：`pgbouncer` 的 transaction 模式对 vector 查询没问题，但要注意 `hnsw.ef_search` 是会话级参数，用 transaction 模式时要在事务内 SET。

## 2.11 版本迁移对照：0.10 前后与 0.11→0.12

### 2.11.1 从 0.9 迁到 0.11+ 的最小动作

```python
# ---- 旧（0.9 及以前） ----
from llama_index import ServiceContext, VectorStoreIndex, SimpleDirectoryReader
from llama_index.vector_stores import QdrantVectorStore

service_context = ServiceContext.from_defaults(
    llm=llm, embed_model=embed_model, node_parser=parser,
    chunk_size=512, chunk_overlap=50,
)
index = VectorStoreIndex.from_documents(docs, service_context=service_context)
query_engine = index.as_query_engine(service_context=service_context)

# ---- 新（0.11+/0.12） ----
from llama_index.core import (
    Settings, VectorStoreIndex, SimpleDirectoryReader, StorageContext,
)
from llama_index.vector_stores.qdrant import QdrantVectorStore

Settings.llm = llm
Settings.embed_model = embed_model
Settings.node_parser = parser            # 切分参数放这里，不再在 ServiceContext 里
Settings.chunk_size = 512                # 仍可用，但推荐直接配 node_parser

storage_context = StorageContext.from_defaults(vector_store=vector_store)
index = VectorStoreIndex.from_documents(docs, storage_context=storage_context)
query_engine = index.as_query_engine()   # 直接吃 Settings，不再传 service_context
```

几个高频改动点：

| 旧 | 新 | 说明 |
| --- | --- | --- |
| `service_context=...` 参数 | 删除该参数，改 `Settings.*` | 部分接口仍保留兼容，但会告警 |
| `LLMPredictor` / `PromptHelper` | 移除 | 上下文窗口由 LLM metadata 自动推断 |
| `from llama_index import ...` | `from llama_index.core import ...` | 顶层包不再导出核心类 |
| `llama_index.vector_stores.X` | `llama_index.vector_stores.x`（子模块） | 每个集成一个包 |
| `node_parser=` 传在 ServiceContext | `Settings.node_parser` 或直接传 pipeline | 行为一致 |

### 2.11.2 0.11 → 0.12 需要注意的

0.12 主要沿两条线演进：**异步优先**（大量 `a*` 方法完善）和 **Workflows 成为编排默认**。对本章影响最大的三点：

1. **依赖包版本约束更紧**。`llama-index-core` 与各集成包的主版本要配套，混装会出现「方法存在但签名不同」的诡异错误。建议用 constraints 文件锁死全组版本。
2. **异步路径要真正 await**。`pipeline.arun()`、`index.ainsert_nodes()`、`retriever.aretrieve()` 在 0.12 上是主要路径；混用同步调用会阻塞事件循环，表现为高并发下延迟整体抬升。
3. **部分默认值调整**（例如默认 callback、默认批大小）。凡是依赖默认值的行为，写显式参数。

具体每个 minor 版本的 breaking change 以官方 release notes 为准——本章不逐条罗列，因为**版本节奏快于文档更新速度**，把判断依据（锁定版本、显式参数、离线评测）固化下来比背 changelog 更可靠。

### 2.11.3 一处必须留意的签名差异

```python
# 有的版本要求显式传 embed_model，有的从 Settings 取；
# 从已有向量库恢复索引时，永远显式传，避免静默用错模型：
index = VectorStoreIndex.from_vector_store(
    vector_store=vector_store,
    embed_model=embed_model,
)
```

## 2.12 上线检查清单

### 索引构建期

- [ ] 每个 Document 都有**稳定 doc_id**（业务主键派生，不是 UUID）
- [ ] collection 名包含 **模型名 + 维度 + 版本**
- [ ] embedding 模型固定，且 `normalize` / 距离度量一致（cosine ↔ 归一化）
- [ ] chunk_size 由评测决定，不是抄的；中文按 token 算，不按字符
- [ ] metadata 字段类型统一（时间用 ISO 字符串或 int，不用 datetime 对象）
- [ ] 高频过滤字段已在向量库侧**建索引**
- [ ] `IngestionPipeline` 的 `transformations` 里显式包含 `embed_model`
- [ ] 先跑 100 条样本验证维度与字段，再全量

### 检索期

- [ ] `similarity_top_k` 与 rerank `top_n` 有明确配比（见 2.7.3）
- [ ] 混合检索的 BM25 侧**中文已分词**（否则等于没开）
- [ ] 有 `similarity_cutoff` 兜底，避免无答案时硬凑
- [ ] 权限过滤在**检索层**，不在 prompt 里
- [ ] 从 `from_vector_store` 恢复时显式传 `embed_model`
- [ ] 异步路径全部 `await`，没有同步调用混入

### 运维期

- [ ] 支持按 `tenant_id` / `doc_id` **批量删除**（GDPR / 客户注销）
- [ ] docstore 外部化或明确纳入备份（多副本部署必须外部化）
- [ ] 埋点覆盖 embed / search / rerank / llm 分段耗时 + top_score + score_gap
- [ ] 有离线评测集（50~100 条 query + 标注），任何策略变更先跑评测
- [ ] 索引重建有一键脚本，且能双写切流（`docs_v2` → 灰度 → `docs_v3`）
