## 0. 版本基线与阅读约定

本章面向 **LlamaIndex 0.11+/0.12+ 主线**（即 `llama_index.core` 命名空间时代）。有几条版本事实必须先钉住，否则你会在网上搜到大量互相矛盾的写法：

| 事实 | 说明 |
| --- | --- |
| **0.10.0 是分水岭** | 命名空间从「顶层 `llama_index` 一把梭」改为 `llama_index.core` 核心 + `llama-index-*` 集成包拆分；全局配置从 `ServiceContext` 换成 `Settings` |

| **0.12+ 的 Agent 是基于 Workflow 重写的** | `llama_index.core.agent.workflow` 下的 `FunctionAgent` / `ReActAgent` / `CodeActAgent` / `AgentWorkflow`，与 0.10 时代 `llama_index.agent` 里的 `AgentRunner` / `OpenAIAgent` 不是一套东西 |
| **当前 PyPI 已到 0.14.x** | 写本章时核实到 `llama-index-core` 为 **0.14.26**、`llama-index-workflows` 为 **2.26.1**。0.11/0.12 的心智模型在 0.14 依然成立，但**导入路径与细节有漂移**，见下面标注 |

> **关于 `llama_index.core.workflow` 的核实结果**：核实源码 `llama-index-core/llama_index/core/workflow/workflow.py`，文件内容只有一行
> `from workflows.workflow import Workflow, WorkflowMeta  # noqa`
> 也就是说 `llama_index.core.workflow` 现在是一个纯转发 shim。`from llama_index.core.workflow import Workflow, step, StartEvent, StopEvent` **仍然可用**，但新代码建议直接用 `workflows` 包，避免哪天 shim 被移除。

## 1. 一句话架构：三个平面

先给你结论，后面所有小节都是这句话的展开。

> **LlamaIndex = 数据面（把私有数据变成可检索的节点）+ 查询面（把检索结果合成进 LLM 上下文）+ 编排面（用事件驱动工作流串起多步决策）。**

三个平面各自有独立的抽象：

```
┌───────────────────────────── 编排面 (Orchestration) ─────────────────────────────┐
│  Workflow（Event / StartEvent / StopEvent / @step / Context）                     │
│    └── Agent = Workflow 的特化：FunctionAgent / ReActAgent / AgentWorkflow        │
└───────────────────────────────────┬──────────────────────────────────────────────┘
                                    │ 把下面这些当「工具」调用
┌───────────────────────────────────▼──────────────────────────────────────────────┐
│ 查询面 (Query)                                                                    │
│   Index ──as_retriever()──▶ Retriever ──▶ NodePostprocessor ──▶ ResponseSynthesizer│
│     │                            └──────────────┬──────────────┘                  │
│     └──as_query_engine()────────────────▶ QueryEngine ──▶ Response                │
│     └──as_chat_engine() ─────────────────▶ ChatEngine  ──▶ (有状态对话)            │
└───────────────────────────────────▲──────────────────────────────────────────────┘
                                    │ 读
┌───────────────────────────────────┴──────────────────────────────────────────────┐
│ 数据面 (Data)                                                                     │
│   Reader ──▶ Document ──IngestionPipeline──▶ Node ──▶ Index ──▶ StorageContext      │
│                (整份文件)      (切分/抽取/嵌入)  (切片)   (访问结构)  ┌────────────┐ │
│                                                                      │ docstore   │ │
│   Settings（全局默认依赖：llm / embed_model / transformations ...）    │ index_store│ │
│                                                                      │ vector_store│ │
│                                                                      └────────────┘ │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**三句话记住依赖方向：**

1. **数据面往下沉**：Document 切成 Node，Node 被嵌入进 vector store，索引结构进 index store，节点正文进 docstore。
2. **查询面往上抽象**：Index 只是「访问策略」；Retriever 是它的一种查询投影；QueryEngine 把「检索 + 后处理 + 合成」固化成一条管道。
3. **编排面横切**：Workflow 不关心数据怎么存，它只消费事件、编排步骤，并把 QueryEngine / Retriever / 任意外部 API 当成工具。

## 2. 数据模型：Document 与 Node

### 2.1 关系：Document 是 TextNode 的子类

这是理解整个数据面的第一个关键事实。官方文档原话：*"the `Document` object is a subclass of our `TextNode` object"*。所以：

- **Document** = 「一整份源文件」这一层语义的节点（PDF、网页、数据库一行）；
- **Node（TextNode）** = 切分后的片段，是**索引与检索的真正单位**；
- 因为继承关系，你在 Document 上设的所有字段（metadata、excluded keys、relationships）都会顺延到它切出来的每个 Node 上。

```python
from llama_index.core import SimpleDirectoryReader, Document

# 方式一：Reader 加载
documents = SimpleDirectoryReader("./data", filename_as_id=True).load_data()

# 方式二：手工构造
documents = [
    Document(text="...", metadata={"source": "wiki", "lang": "zh"}),
]
```

### 2.2 Node 的字段：哪些字段会「偷偷」影响效果和成本

| 字段 | 作用 | 生产中的坑 |
| --- | --- | --- |
| `text` | 节点正文 | 切分策略决定它 |
| `node_id` | 节点唯一 ID，不指定则自动生成 | 自己生成要保证稳定，否则增量更新会全量重写 |
| `doc_id` / `ref_doc_id` | 指向源文档 | 文档管理的锚点，见 §7 |
| `metadata` | 键值对，随节点走 | **默认会被注入正文**，同时参与 embedding 和 LLM 提示 |
| `excluded_embed_metadata_keys` | 不参与 embedding 的 metadata 键 | 时间戳这类高熵字段应当排除 |
| `excluded_llm_metadata_keys` | 不进 LLM 提示的 metadata 键 | 内部 ID、权限标记应当排除 |
| `relationships` | 与其它节点的关系 | 支撑 auto-merging / sentence-window 等高级检索 |
| `embedding` | 向量 | 换 embedding 模型必须重建全部向量 |

**metadata 默认注入文本**这一点值得单独强调：它意味着「给 Document 加一堆 metadata」不是零成本的——它会改变 embedding 的语义、占用上下文窗口、并可能引入噪声。正确姿势是**要用的显式保留，不用的显式排除**（✅ 官方文档 §Defining and Customizing Documents 明确说明默认注入）。

### 2.3 relationships：高级检索的地基

```python
from llama_index.core.schema import TextNode, NodeRelationship, RelatedNodeInfo

node1 = TextNode(text="前一段", id_="n1")
node2 = TextNode(text="后一段", id_="n2")

node1.relationships[NodeRelationship.NEXT] = RelatedNodeInfo(node_id=node2.node_id)
node2.relationships[NodeRelationship.PREVIOUS] = RelatedNodeInfo(node_id=node1.node_id)
# 也支持 PARENT / CHILD / SOURCE
```

这些关系不是装饰品，它们直接决定了几类检索增强是否可用：

- `PREVIOUS` / `NEXT` → `PrevNextNodePostprocessor`（命中一片就带上下文）；
- `PARENT` / `CHILD` → small-to-big、auto-merging retrieval；
- `SOURCE` → 回溯到整份文档，做引用与溯源。

**架构含义**：如果你的切分器把关系信息丢了，后面想加「上下文扩展」就只能重建索引。**切分策略要在第一天就按未来的检索需求设计，而不是按默认值跑通就行。**

### 2.4 切分：NodeParser / TextSplitter

```python
from llama_index.core.node_parser import SentenceSplitter

parser = SentenceSplitter(chunk_size=512, chunk_overlap=20)
nodes = parser.get_nodes_from_documents(documents)
```

⚠️ **需对照官方文档核实**：`Settings` 上同时存在 `text_splitter` 与 `node_parser` 两个入口——官方「Configuring Settings」页用的是 `Settings.text_splitter = SentenceSplitter(...)`，而「ServiceContext → Settings 迁移」页写的是 `Settings.node_parser = SentenceSplitter(...)`。两者在多数版本里指向同一个底层字段，但**请以你锁定版本的 `Settings` 属性列表为准**，不要在两个名字之间来回横跳。

## 3. Index：不是数据库，是「访问策略」

### 3.1 最容易踩的心智误区

`VectorStoreIndex` 给人的第一印象是「索引 = 向量库」。**错。** 索引对象本身非常轻，它只持有：

1. **index_struct**：索引的结构描述（一个 `IndexStructType` + 摘要信息），落在 **index_store**；
2. 对 **docstore** 的引用（节点正文的来源）；
3. 对 **vector_store** 的引用（向量的来源）。

真正的数据在三层存储里（见 §8）。所以：

> **Index 决定「怎么访问数据」，StorageContext 决定「数据存在哪」。这两件事必须分开理解。**

### 3.2 索引家族与选择

| 索引 | 访问策略 | 典型场景 | 代价 |
| --- | --- | --- | --- |
| `VectorStoreIndex` | top-k 语义检索 | 绝大多数 RAG | 需 embedding，成本随文档量线性 |
| `SummaryIndex`（旧名 `ListIndex`） | 顺序遍历全部节点 | 全量总结、小语料 | LLM 调用随节点数线性增长 |
| `DocumentSummaryIndex` | 先按文档摘要路由，再检索 | 多文档、需要「选文档」 | 建索引时每篇文档一次 LLM 调用 |
| `KeywordTableIndex` / `RAKEKeywordTableIndex` | 关键词倒排 | 精确术语、低资源 | 召回靠词表，语义弱 |
| `TreeIndex` | 自底向上建树摘要 | 层级总结 | 建树成本高 |
| `PropertyGraphIndex` / `KnowledgeGraphIndex` | 图结构检索 | 实体关系、多跳 | schema 设计与抽取成本高 |

**判断规则**：默认 `VectorStoreIndex`；只有当「检索失败的原因是结构性的」（如需要跨文档路由、需要多跳关系、需要全量总结）时才换索引，而不是因为向量检索效果差就换——先修切分、metadata、rerank。

### 3.3 Index 的三次投影

```python
from llama_index.core import VectorStoreIndex

index = VectorStoreIndex.from_documents(documents)

retriever      = index.as_retriever(similarity_top_k=5)   # 只要"找"，不要"答"
query_engine   = index.as_query_engine()                  # "找 + 答"
chat_engine    = index.as_chat_engine()                    # "找 + 答 + 记住上下文"
```

这三个方法**不是三个不同的对象**，而是同一个索引按不同「关注点」暴露的三张脸。理解这一点，你就能回答「我该拿 Retriever 还是 QueryEngine」——答案取决于你需要不需要 LLM 合成那一步。

### 3.4 构建 vs 重载

```python
# 首次构建
index = VectorStoreIndex.from_documents(documents, storage_context=storage_context)

# 已存在则直接挂载（不重新切分、不重新嵌入）
index = VectorStoreIndex.from_vector_store(vector_store=vector_store)
```

`from_documents` 会**跑一遍 ingestion（切分 + 嵌入 + 写入三层存储）**；`from_vector_store` 什么都不做，只做「挂载」。把这两者混用是「重启服务就重复嵌入几万条数据」的主要原因。

## 4. 查询面：Retriever / Postprocessor / Synthesizer / QueryEngine

### 4.1 官方定义的三段式

查询在三段式上展开（✅ 官方文档 §Querying 原文）：

1. **Retrieval**：从 Index 找出最相关的节点（最常见是 top-k 语义检索）；
2. **Postprocessing**：可选的重排、过滤、改写、上下文扩展；
3. **Response synthesis**：把查询 + 相关数据 + 提示一起送进 LLM，产出回答。

`QueryEngine` 就是这条管道的封装。**你能调的每一个旋钮，都落在这三段之一。**

### 4.2 手工组装：把黑盒打开

```python
from llama_index.core import VectorStoreIndex, get_response_synthesizer
from llama_index.core.retrievers import VectorIndexRetriever
from llama_index.core.query_engine import RetrieverQueryEngine
from llama_index.core.postprocessor import SimilarityPostprocessor

index = VectorStoreIndex.from_documents(documents)

retriever = VectorIndexRetriever(index=index, similarity_top_k=10)          # ① 召回放宽
response_synthesizer = get_response_synthesizer()                            # ③ 合成策略
query_engine = RetrieverQueryEngine(
    retriever=retriever,
    response_synthesizer=response_synthesizer,
    node_postprocessors=[SimilarityPostprocessor(similarity_cutoff=0.7)],    # ② 收紧精度
)

response = query_engine.query("作者小时候做了什么？")
print(response.response)
print([n.score for n in response.source_nodes])
```

这就是「**召回放宽、精度收紧**」的标准结构：`similarity_top_k` 调大保证不漏，后处理按分数/关键词裁掉噪声。它比单纯调 `as_query_engine(similarity_top_k=...)` 更容易定位问题——因为每一段的输入输出你都能单独打印。

### 4.3 response_mode：成本与质量的直接开关

```python
query_engine = RetrieverQueryEngine.from_args(retriever, response_mode="compact")
```

| `response_mode` | 机制 | LLM 调用量 | 适用 |
| --- | --- | --- | --- |
| `default` | create-and-refine：逐节点迭代改写答案 | **O(n)**，每个节点一次 | 需要详尽答案、节点少 |
| `compact` | 每个提示塞满能塞的节点，塞不下再 refine | **介于两者之间** | 默认首选，成本/质量平衡 |
| `tree_summarize` | 递归建树归并 | **O(log n) 层** | 总结类任务 |
| `no_text` | 只跑检索，不调 LLM | **0** | 调试召回、离线评估 |
| `accumulate` | 每个节点各答一次再拼接 | **O(n)** | 同一问题对每段分别作答 |

**架构含义**：`no_text` 是排查「答得不对」的第一件工具——先用它确认**召回到了正确节点**，再去怀疑合成；否则你会一直在提示词上打转。这也是评估体系该有的第一层：检索质量与合成质量必须分开度量。

### 4.4 Response 对象

`query_engine.query(...)` 返回的不是字符串，而是 `Response`：

- `response`：最终答案文本；
- `source_nodes`：参与合成的节点（含 `score`、`metadata`）——**这是做引用、审计、幻觉归因的唯一依据**；
- `metadata`：合成过程附加信息。

生产环境里，**永远把 `source_nodes` 一起落库**。用户投诉「答错了」时，你能立刻判断是没召回、召回了但合成错、还是数据本身错。

## 5. ChatEngine：QueryEngine 的有状态外壳

### 5.1 它解决什么问题

`QueryEngine.query()` 是**无状态**的：问「那它的作者是谁？」时，它不知道「它」指什么。`ChatEngine` 补的就是这一段——把「历史对话 + 当前问题」压缩成一个独立可检索的查询，再走 QueryEngine 的管道。

### 5.2 四种内置实现与选择

✅ 已核实 `llama_index/core/chat_engine/__init__.py` 的导出：

| 类 | 机制 | 何时用 |
| --- | --- | --- |
| `SimpleChatEngine` | 纯 LLM 对话，不检索 | 闲聊、无知识库场景 |
| `ContextChatEngine` | 每次把检索到的上下文塞进系统提示 | 单轮明确、历史简单 |
| `CondenseQuestionChatEngine` | 先把历史 + 问题压缩成一个独立问题，再检索 | 多轮指代多，但不需要重排上下文 |
| `CondensePlusContextChatEngine` | **压缩问题 + 每轮重检索 + 维护上下文** | **RAG 聊天机器人的默认答案** |
| `MultiModalContextChatEngine` / `MultiModalCondensePlusContextChatEngine` | 多模态版本 | 图文混合知识库 |

```python
chat_engine = index.as_chat_engine(chat_mode="condense_plus_context")
resp = chat_engine.chat("作者小时候做了什么？")
resp = chat_engine.chat("那他的父母呢？")   # 能正确解析"他"
chat_engine.reset()
```

⚠️ **需对照官方文档核实**：`as_chat_engine(chat_mode=...)` 的 `chat_mode` 字符串取值（如 `"simple"` / `"context"` / `"condense_question"` / `"condense_plus_context"` / `"react"` / `"best"`）在不同版本间有过增删，尤其 `"react"` / `"openai"` / `"function"` 这类旧模式在 0.11+ 已明确不再推荐。**稳妥做法是直接用上表中的类显式构造**，而不是依赖字符串。

### 5.3 会话持久化

ChatEngine 的状态默认在内存（`memory`）。要跨进程/重启保留会话，需要 **chat store**（`llama_index.core.storage.chat_store` 下的 `SimpleChatStore` / `RedisChatStore` 等），配合 `memory=ChatMemoryBuffer.from_defaults(chat_store=..., chat_store_key=...)`。✅ 官方 storage 文档列出 `Chat Stores` 为独立存储层。

### 5.4 什么时候不要用 ChatEngine

- 需要**工具调用、条件分支、人审**：直接上 `FunctionAgent` / `Workflow`，ChatEngine 的对话循环太固定；
- 需要**严格的会话隔离与权限控制**：ChatEngine 默认没有租户概念，`chat_store_key` 是你的隔离边界，别用同一个 key 服务所有用户；
- 需要**可回放的中间步骤**：ChatEngine 只吐最终响应，Workflow 才能吐事件流。

## 6. 编排面：Agent 与 Workflow

### 6.1 一句话关系

> **Agent 是 Workflow 的一个特化。** Workflow 是底层的「步骤 + 事件」运行时；Agent 是「LLM 决策 + 工具调用」这一特定拓扑的预置实现。

这条关系是 0.12+ 与 0.10 时代最大的认知差别：0.10 的 `AgentRunner` 是一套独立循环，与 Workflow 无关；0.12+ 的 `FunctionAgent` 本身就是 `Workflow` 的子类，所以**流式输出、状态、超时、可观测性全部继承**。

### 6.2 预置 Agent

✅ 已核实 `llama_index/core/agent/workflow/__init__.py` 导出：`FunctionAgent` / `ReActAgent` / `CodeActAgent` / `AgentWorkflow` / `AgentContext` / `BaseWorkflowAgent`，以及事件类型 `AgentInput` / `AgentStream` / `AgentOutput` / `ToolCall` / `ToolCallResult`。

```python
from llama_index.core.agent.workflow import FunctionAgent
from llama_index.llms.openai import OpenAI

def multiply(a: float, b: float) -> float:
    """把两个数相乘并返回乘积"""      # docstring 就是工具的说明书
    return a * b

agent = FunctionAgent(
    tools=[multiply],
    llm=OpenAI(model="gpt-4o-mini"),
    system_prompt="你是一个会使用工具完成数学计算的助手。",
    streaming=False,          # 某些模型不支持流式时关掉
)

# 注意：run 是 async
response = await agent.run(user_msg="20+(2*4) 等于多少？")
```

三个工程细节，官方教程里都提到但容易被忽略：

1. **工具就是普通 Python 函数**：函数名、类型注解、docstring 共同构成给 LLM 的 schema。docstring 写得含糊，工具就不会被正确调用。
2. **`run` 是异步的**：直接写在脚本里要 `asyncio.run(main())`，写在 FastAPI/Notebook 里天然可用。
3. **`streaming=True` 是默认值**：模型不支持流式时它会报错，此时显式 `streaming=False`。

### 6.3 自己写 Workflow

Workflow 的模型极简，只有四个概念：

| 概念 | 含义 |
| --- | --- |
| `Event` | 步骤之间传递的消息（`StartEvent` / `StopEvent` 是两端哨兵） |
| `@step` | 一个 async 方法即一个步骤 |
| **参数类型标注** | **决定这个步骤订阅哪种事件**——这是 Workflow 唯一的「连线」方式 |
| **返回类型标注** | **决定它发布哪种事件**——决定下一步谁被触发 |
| `Context` | 跨步骤共享状态、收集事件、序列化恢复 |

```python
from workflows import Workflow, step, Context          # 新路径（0.11+ 独立包）
from workflows.events import Event, StartEvent, StopEvent

class Retrieved(Event):
    text: str

class NeedMore(Event):
    reason: str

class QaFlow(Workflow):
    @step
    async def retrieve(self, ctx: Context, ev: StartEvent) -> Retrieved | NeedMore:
        docs = await my_retriever.aretrieve(ev.question)
        if not docs:
            return NeedMore(reason="empty")
        ctx.store["docs"] = [d.text for d in docs]
        return Retrieved(text=docs[0].text)

    @step
    async def answer(self, ev: Retrieved) -> StopEvent:
        return StopEvent(result=f"基于以下内容回答：{ev.text}")

    @step
    async def retry(self, ev: NeedMore) -> StopEvent:
        return StopEvent(result="知识库里没有相关内容")

flow = QaFlow(timeout=30)
result = await flow.run(question="...")
```

**要点解读：**

- `retrieve` 的返回类型是 `Retrieved | NeedMore` → 两个分支步骤同时被订阅，**这是 Workflow 里的 if/else**；
- 一个步骤可以只写 `ev: Retrieved` 而不要 `ctx`，也可以只要 `ctx`，执行器按类型注入；
- 想让多个步骤**并行**，就让它们订阅同一个事件（扇出），再用 `ctx.collect_events(...)` 汇聚（⚠️ `collect_events` 的确切签名需对照官方 workflows 文档核实）；
- `timeout` 是运行级超时，超时抛 `WorkflowTimeoutError`；
- 用 `ctx.store` 存的状态可以序列化，从而支持「跑一半持久化、之后恢复」——这是 Workflow 相比「一大坨 if-else」的核心优势。

### 6.4 两条导入路径怎么选

```python
# 路径 A：独立包（0.11+ 推荐，官方 workflows 文档用这个）
from workflows import Workflow, step, Context
from workflows.events import Event, StartEvent, StopEvent

# 路径 B：core 垫片（向后兼容，仍可用）
from llama_index.core.workflow import Workflow, step, Context, StartEvent, StopEvent
```

**两者是同一套类**（路径 B 的模块内部就是 `from workflows.workflow import ...`，✅ 已核实源码）。新项目用 A，读旧代码看到 B 也不用改。

## 7. IngestionPipeline：离线数据面的流水线

### 7.1 为什么它必须是独立一层

「`VectorStoreIndex.from_documents()` 一把跑通」在 demo 里很好，在真实系统里会立刻暴露三个问题：

1. **重复计算**：源文件没变也要重新切分、重新嵌入；
2. **无法增量**：改一个文件就全量重建；
3. **不可组合**：想在切分和嵌入之间插入「标题抽取」「元数据补全」「去重」就无处下手。

`IngestionPipeline` 就是这三个问题的答案。

```python
from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core.extractors import TitleExtractor
from llama_index.embeddings.openai import OpenAIEmbedding
from llama_index.core.storage.docstore import SimpleDocumentStore

pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_size=512, chunk_overlap=20),   # ① 切分
        TitleExtractor(),                                       # ② 抽取（会调 LLM）
        OpenAIEmbedding(),                                      # ③ 嵌入
    ],
    docstore=SimpleDocumentStore(),   # 开启文档管理（去重/增量）
)

nodes = pipeline.run(documents=documents)
```

### 7.2 transformations 的顺序是有语义的

顺序不是随便排的：**切分必须在抽取之前**（抽取按节点工作）、**嵌入必须在最后**（避免对将被过滤的节点浪费调用）。Pipeline 里`每个 node × transformation` 的组合都会被哈希缓存，所以顺序一变，缓存全失效。

### 7.3 直写向量库：必须保留 Embedding 阶段

```python
pipeline = IngestionPipeline(
    transformations=[SentenceSplitter(...), OpenAIEmbedding()],
    vector_store=vector_store,        # 直接写入远端向量库
)
pipeline.run(documents=documents)

# 之后挂载（不再重复嵌入）
from llama_index.core import VectorStoreIndex
index = VectorStoreIndex.from_vector_store(vector_store)
```

✅ 官方文档明确警告：**如果接了 vector store，Embedding 必须是 pipeline 的一个阶段**，否则后续 `from_vector_store` 实例化索引会失败（缺 embedding 字段）。反之，不接 vector store、只产出节点列表时，可以省掉嵌入。

### 7.4 缓存与持久化

```python
pipeline.persist("./pipeline_storage")            # 存缓存
new_pipeline = IngestionPipeline(transformations=[...])
new_pipeline.load("./pipeline_storage")           # 载入缓存，重跑几乎瞬间完成
```

远端缓存（`RedisCache` / `MongoDBCache` / `FirestoreCache`）通过 `IngestionCache(cache=..., collection=...)` 接入，接入后无需 `persist`，边跑边写。

### 7.5 文档管理（document management）：增量的关键

接了 `docstore` 之后，pipeline 会维护 `doc_id → document_hash` 映射，行为如下（✅ 官方文档 §Document Management）：

| 场景 | 行为 |
| --- | --- |
| 接了 vector store + `doc_id` 已存在 + hash 变了 | 重新处理并 **upsert** |
| 接了 vector store + `doc_id` 已存在 + hash 没变 | **跳过** |
| 没接 vector store | 只按节点哈希去重，无法删除旧节点 |

**关键约束**：`doc_id` 必须稳定。用 `SimpleDirectoryReader(..., filename_as_id=True)` 或自己给业务主键，**绝不要让 doc_id 随机生成**——否则每次跑都是「全新增」，hash 去重完全失效。

### 7.6 与 index.from_documents 的关系

`VectorStoreIndex.from_documents()` 内部也会跑一套默认 transformations（`Settings.transformations`）。所以：

- **原型阶段**：`from_documents` 足够；
- **生产阶段**：用 `IngestionPipeline` 负责「进数据的唯一入口」，索引侧只用 `from_vector_store` 挂载。**一个系统里只留一条写入路径**，否则 docstore 与 vector store 会不一致。

## 8. Storage 三层：docstore / index_store / vector_store

### 8.1 全景表

✅ 官方 storage 文档列出五类存储（外加 Property Graph store）：

| 存储 | 存什么 | 默认实现 | 何时必须换 |
| --- | --- | --- | --- |
| **docstore**（Document store） | 节点的**正文 + metadata + relationships** | `SimpleDocumentStore` | 需要跨机共享、需要按 ID 增量更新 |
| **index_store**（Index store） | 索引的**结构元数据**（`index_struct`） | `SimpleIndexStore` | 多索引、需要多处挂载同一索引 |
| **vector_store**（Vector store） | **向量 +（通常）正文副本 + metadata** | `SimpleVectorStore` | 数据量超过内存、需要水平扩展 |
| **kv_store** | 底层键值抽象，上面两个都建在它之上 | `SimpleKVStore` | 换后端时统一替换 |
| **chat_store** | 会话消息 | `SimpleChatStore` | 多副本会话、需要 TTL |
| **property graph store** | 知识图谱 | 各图数据库实现 | `PropertyGraphIndex` |

### 8.2 装配：StorageContext

```python
from llama_index.core import StorageContext
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core.storage.index_store import SimpleIndexStore
from llama_index.core.vector_stores import SimpleVectorStore

storage_context = StorageContext.from_defaults(
    docstore=SimpleDocumentStore(),
    index_store=SimpleIndexStore(),
    vector_store=SimpleVectorStore(),
)
```

`StorageContext` 是一个**纯装配对象**：它不含业务逻辑，只回答「这几个 store 分别是谁」。把它显式传进 `from_documents` / `IngestionPipeline`，是让数据落点可控的唯一方式。

### 8.3 持久化与重载

```python
# 落盘（JSON 形式，写出 docstore.json / index_store.json / default__vector_store.json）
index.storage_context.persist(persist_dir="./storage")

# 重载
from llama_index.core import load_index_from_storage
storage_context = StorageContext.from_defaults(persist_dir="./storage")
index = load_index_from_storage(storage_context)
```

✅ 官方文档说明：LlamaIndex 的持久化基于 **fsspec**，因此理论上可落到本地磁盘、S3、Cloudflare R2 等后端。

### 8.4 一个必须想清楚的问题：谁是真相源

外部向量库（Qdrant / Pinecone / Milvus / pgvector …）**通常同时保存文本、向量和 metadata**。这意味着：

- **可以不配 docstore**：`VectorStoreIndex.from_vector_store(vs)` 就能工作，检索到的节点自带文本；
- **但 docstore 仍建议配**：文档管理（`doc_id → hash`）、引用溯源、跨库一致性检查都依赖它；
- **FAISS 是例外**：它只存向量，**必须**配 docstore，否则你只有向量没有正文。

**决策规则**：

> 只读、数据由外部系统同步 → 可以不配 docstore；有「增量更新 / 删除 / 权限过滤 / 审计溯源」任一需求 → 必须配 docstore，并把它当真相源。

### 8.5 存储层的四个典型故障

| 故障现象 | 根因 | 排查动作 |
| --- | --- | --- |
| 重启后回答质量骤降 | 只 persist 了 vector store，docstore/index_store 没落盘 | 检查 `persist_dir` 下是否三份都在 |
| 文档更新后出现重复结果 | `doc_id` 不稳定，走成了全新增 | 打印 `node.ref_doc_id`，用稳定业务主键 |
| `from_vector_store` 报缺 embedding | pipeline 里漏了 Embedding 阶段 | 见 §7.3 |
| 删除文档后仍被检索到 | 只删了 docstore，没删 vector store（或反之） | 用 document management / 显式 `delete_ref_doc`，⚠️ 具体 API 需对照官方文档核实 |

## 9. Settings：全局默认依赖的容器

### 9.1 它到底是什么

`Settings` 是**一个进程级单例**，装的是「被到处复用、但只该配置一次」的东西。它的两个设计特征决定了它的用法：

1. **懒实例化**：`Settings.llm` 只有在真正被某个模块需要时才加载。这是它取代 `ServiceContext` 的核心理由——旧方案会把所有组件在启动时就实例化，哪怕你根本不用；
2. **兜底注入**：任何接口在**没收到显式参数**时，从 `Settings` 取默认值。

```python
from llama_index.core import Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding
from llama_index.core.node_parser import SentenceSplitter

Settings.llm = OpenAI(model="gpt-4o-mini", temperature=0.1)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small", embed_batch_size=100)
Settings.node_parser = SentenceSplitter(chunk_size=512, chunk_overlap=20)
Settings.context_window = 8192
Settings.num_output = 512
```

### 9.2 属性分层：三类配置别混用

| 类别 | 属性 | 作用范围 | 误用后果 |
| --- | --- | --- | --- |
| **模型** | `llm`、`embed_model` | 全局默认 | 测试环境误用生产 Key；换模型后旧向量失效 |
| **数据加工** | `node_parser` / `text_splitter`、`transformations`、`chunk_size` / `chunk_overlap` | 全局默认，影响**写入** | 改 chunk_size 等于要求重建索引，但系统不会提醒你 |
| **运行时约束** | `context_window`、`num_output`、`tokenizer`、`callback_manager` | 全局默认，兜底提示组装与计量 | tokenizer 与模型不匹配 → 截断位置算错 |

### 9.3 分层覆盖规则：局部永远赢

```python
# 全局默认（一般用在应用启动处）
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")

# 局部覆盖（只影响这一次调用）
index = VectorStoreIndex.from_documents(
    documents, embed_model=my_other_embed_model, transformations=[...]
)
query_engine = index.as_query_engine(llm=my_cheaper_llm, similarity_top_k=8)
```

规则只有一条：**显式传参 > Settings 默认**。所以：

- 「我明明改了 Settings，为什么没生效？」——99% 是因为某处显式传了参数；
- 「我不想让某个模块用 OpenAI」——设置 `Settings.llm` / `Settings.embed_model` 后，**任何不显式传参的模块**都不会再用 OpenAI。✅ 官方迁移文档把这写作「确保框架永远不会用到 OpenAI」的手段。

### 9.4 生产纪律

1. **只在一个入口函数里设 Settings**（`config.py` / `app startup`），不要散落在业务代码里；
2. **写库时用的 embed_model 必须固化下来**（记进配置或 metadata），换模型 = 重建向量，这是运维视角的硬约束；
3. **多租户 / 多模型并存**：不要动 `Settings`，一律走局部传参；
4. **不要把它当依赖注入容器滥用**：`Settings` 只装 LlamaIndex 认识的几个组件，业务依赖（数据库连接、HTTP 客户端）不该塞进来。

这一节是为了让你在搜到 2023 年的博客时不至于照着写错。

| 主题 | 0.10 之前（旧写法） | 0.10+ / 0.11+ / 0.12+（新写法） |
| --- | --- | --- |
| 导入 | `from llama_index import VectorStoreIndex, SimpleDirectoryReader` | `from llama_index.core import VectorStoreIndex, SimpleDirectoryReader` |

**关于安装包**：`llama-index` 是「全家桶 meta 包」，会拖进大量集成；生产项目建议只装 `llama-index-core` + 你真正用到的 `llama-index-llms-*` / `llama-index-embeddings-*` / `llama-index-vector-stores-*` / `llama-index-readers-*`。这既是体积问题，也是「依赖冲突排查难度」问题。

## 11. 与 LangChain / LangGraph 的定位差异

两者经常被当成竞品，实际上**切入的问题不同**。先把结论给出，再给对比。

> **LlamaIndex 把「私有数据的索引与检索」当一等公民，主张「检索质量决定回答质量」；LangChain 把「模型/工具/集成的广度与链式编排」当一等公民，主张「万物皆 Runnable，可拼可换」。**

### 11.1 对比表

| 维度 | LlamaIndex | LangChain |
| --- | --- | --- |
| **核心抽象** | `Document → Node → Index → Retriever → QueryEngine`，外加 `Workflow` | `Runnable`（LCEL 管道）、`Tool`、`Retriever`（较薄）、`LangGraph`（图状态机） |
| **主打问题** | RAG / 数据问答 / 文档 Agent | 通用 LLM 应用编排 + 集成广度 |
| **检索能力** | **深**：多种索引结构、节点关系、后处理链、response_mode 成本开关、评估工具 | **浅**：Retriever 接口统一但索引结构少，深度靠外部 |
| **组合方式** | 索引投影（`as_query_engine`）+ 事件驱动 Workflow | LCEL 的 `| ` 管道 + LangGraph 的节点/边 |
| **状态与恢复** | Workflow 的 `Context` 可序列化恢复；ChatEngine 有 chat store | LangGraph 的 checkpointer 更成熟（时间旅行、人工中断） |
| **数据接入** | 数百个 `llama-index-readers-*`，且节点模型是「检索意识」的 | 社区 loader 生态更杂，切分/元数据语义不如前者统一 |
| **可观测性** | 内置 instrumentation，可接 Phoenix / OpenTelemetry | LangSmith（商业产品体验最好） |
| **学习曲线** | 概念少但「索引与检索」的隐式规则多（切分、metadata 注入、response_mode） | 概念多（Runnable / 各种 Chain / Graph），但面条式拼装门槛低 |

### 11.2 三个真正能区分场景的差异

**① 有没有「索引」这一层。**
LangChain 里没有和 `Index` 对等的东西——它把「怎么检索」交给 `VectorStore.as_retriever()`，而 LlamaIndex 的 `Index` 是「访问策略」的抽象（向量/摘要/关键词/图）。**如果你需要「同一份数据用不同策略访问」，LlamaIndex 的抽象更顺；如果你只是「一个向量库 + top-k」，两者差别不大。**

**② 默认值的方向不同。**
LlamaIndex 的默认值偏向「RAG 最佳实践」（自动切分 + 自动嵌入 + 默认 synthesizer）；LangChain 的默认值偏向「最小可组合单元」（你几乎总要自己拼 `prompt | model | parser`）。**前者开发快、后者可控性强**——但要小心 LlamaIndex 的默认值会「替你做决定」（比如 metadata 默认注入文本）。

**③ 编排层的成熟度方向。**
LlamaIndex 的 `Workflow` 是「事件驱动 + 步骤订阅事件」，写起来像异步消息流；LangGraph 是「显式图 + 检查点」，写起来像状态机。**需要人工中断、时间旅行、复杂恢复 → LangGraph 目前更成熟；需要「LLM 决策 + 工具循环」这类 Agent 拓扑 → LlamaIndex 的 `FunctionAgent` 开箱即用。**

### 11.3 能不能混用

能，而且很常见。两种务实组合：

- **LlamaIndex 做数据与检索，LangGraph 做编排**：用 `IngestionPipeline` + `VectorStoreIndex` 建库，把 `index.as_retriever()` 包成一个 LangGraph 节点。好处是检索侧用成熟抽象，编排侧用成熟状态机。
- **LlamaIndex 做全栈，LangChain 只借工具**：把 LangChain 的 `Tool` 或 `@tool` 函数直接塞进 `FunctionAgent(tools=[...])`（工具只要是可调用 + 有类型注解与 docstring 即可）。

**不建议**：为了「两边都用上」而引入双套抽象，把 `Retriever`、`Document`、`Node` 在两边来回转换——转换层带来的 bug 会超过收益。

### 11.4 三方对照：LlamaIndex / LangChain / LangGraph

前两节讲的是 LlamaIndex 与 LangChain 的差异。实际上三者**不在同一个比较维度**：LlamaIndex 与 LangChain 是「应用框架」，LangGraph 是「编排引擎」（它构建在 LangChain 的运行时之上，但不负责数据接入与索引）。

| 维度 | LlamaIndex | LangChain | LangGraph |
| --- | --- | --- | --- |
| **核心抽象** | `Document → Node → Index → Retriever → QueryEngine`；编排用 `Workflow` | `Runnable`（LCEL 管道）、`Tool`、较薄的 `Retriever` | `StateGraph`、节点/边、`Checkpointer` |
| **最强的地方** | RAG：多索引结构、节点关系、后处理链、`response_mode` 成本开关、评测工具 | 模型与工具接入最广，拼装速度最快 | 有状态、可循环、可中断、断点续跑、人工介入 |
| **数据面（加载/切分/索引）** | **一等公民**，ingestion 全链路内建 | 有 loader/splitter/vectorstore 集成，但要自己拼 | **不提供**，需接 LlamaIndex / LangChain 或原生代码 |
| **编排写起来像** | 事件驱动消息流（步骤订阅事件） | `a \| b \| c` 线性管道 | 显式图 + 图状态 |
| **状态与恢复** | Workflow 的 `Context` 可序列化恢复；ChatEngine 有 chat store | 弱，状态一般自己管 | **最强**（checkpoint、时间旅行、跨进程恢复） |
| **可观测性** | 内置 instrumentation，可接 Phoenix / OpenTelemetry | LangSmith（商业体验最好） | LangSmith + LangGraph Platform |
| **学习曲线** | 概念少，但检索侧的隐式规则多 | 概念多，面条式拼装门槛低 | 需要图思维，简单场景偏重 |
| **主要风险** | 拆包剧烈（0.10），旧教程大面积失效 | 抽象层变动频繁（0.1→0.3），版本漂移 | 简单流程被过度工程化 |

### 11.5 选型判据（按你的场景对号入座）

1. **核心需求是「把私有文档答明白」** → LlamaIndex 起步。它的默认值就是按 RAG 最佳实践调的，省掉大量拼装工作。
2. **核心需求是「接十几家模型和工具、做通用 LLM 应用」** → LangChain。它的集成面与生态最广。
3. **核心需求是「多步流程、人工审核、失败后精确恢复、多 Agent 协作」** → LangGraph 做编排，检索与工具层交给 LlamaIndex 或 LangChain。
4. **四点自检**：
   - 控制流是线性的还是带环的？带环、需要重试或回退 → 图。
   - 流程跑到一半会停（等人审批）吗？会 → 需要 checkpointer。
   - 失败后能否从中间步骤继续？要 → 图 + 持久化状态。
   - 只是「检索 + 一次生成」？→ 直接 QueryEngine，别上图。

**反模式**：为了「三个都用上」而引入多套抽象，在 `Document`、`Node`、`Retriever` 之间来回转换。转换层的 bug 和性能损耗会超过收益。选一个主框架，其余只按需借用单点能力。

## 12. 什么时候用 QueryEngine，什么时候用 Workflow

这是本章最该被记住的一节。判断标准不是「哪个更高级」，而是**你的控制流有多复杂**。

### 12.1 决策表

| 你的需求 | 选择 | 理由 |
| --- | --- | --- |
| 单轮问答、检索即答 | **QueryEngine** | 三段式已经覆盖，写 Workflow 是纯开销 |
| 多轮对话、需要记住上文 | **ChatEngine** | QueryEngine 的无状态外壳已做好 |
| 需要调整召回/重排/合成 | **QueryEngine**（`RetrieverQueryEngine` 手工组装） | 每段都可单独替换 |
| 答案需要结构化（Pydantic） | **QueryEngine + 结构化输出** | 不必上编排层 |
| 需要「先查库，查不到再查 API」 | **Workflow** | 条件分支 + 多数据源 = 控制流 |
| 需要工具调用循环（Agent） | **FunctionAgent / AgentWorkflow** | 预置拓扑，别手写 |
| 需要多步、可重试、可中断、人审 | **Workflow** | 事件流 + 上下文状态 + 超时 |
| 需要把中间步骤暴露给前端（进度条/事件流） | **Workflow** | 步骤级事件可订阅、可流式 |
| 需要跑一半持久化、之后恢复 | **Workflow** | `Context` 可序列化 |
| 需要并行多个检索/多个模型调用再汇总 | **Workflow** | 事件扇出 + 汇聚 |
| 只是想把「检索结果」喂给一个固定 prompt | **Retriever**（连 QueryEngine 都不用） | 你要的是节点，不是答案 |

### 12.2 演进路径：不要一上来写 Workflow

推荐的三段式演进，也是真实项目里最省事的路径：

```
阶段 1  用 QueryEngine 打通「能不能召回到正确节点」
          └─ 用 response_mode="no_text" 单独看 source_nodes
阶段 2  用 RetrieverQueryEngine 手工组装，把召回率/精度调到可接受
          └─ 此时你才有资格谈"合成质量"
阶段 3  业务长出控制流（分支/重试/多源/人审）时，再把阶段 2 的 query_engine
          包成一个 Workflow 步骤 / 一个 Agent 工具
```

**为什么不能反过来**：Workflow 会把「检索质量差」伪装成「编排逻辑问题」。当你在十个步骤里排查「为什么答错了」，成本是单条 QueryEngine 的十倍。**先用最窄的管道验证检索，再上编排。**

### 12.3 反模式清单

| 反模式 | 症状 | 正确做法 |
| --- | --- | --- |
| 用 Workflow 写「一问一答」 | 几十行代码实现了一行 `as_query_engine()` | 直接 QueryEngine |
| 用 QueryEngine 硬凑多步 | 在 prompt 里写「第一步…第二步…」 | 拆成 Workflow 步骤 |
| 用 Agent 做确定性流程 | 明明步骤固定，却让 LLM 每次重新决定走哪条路（贵且不稳） | Workflow 里写死分支，只在需要判断处调 LLM |
| 用 ChatEngine 做工具调用 | 反复在 memory 里塞工具结果 | FunctionAgent |
| 在 Workflow 里手动维护全局变量 | 步骤间靠模块级 dict 传状态 | `ctx.store` |

## 13. 心智模型常见误区（速查）

1. **「Index 就是向量库」** → Index 是访问策略，数据在 docstore/index_store/vector_store。
2. **「`from_documents` 会自动持久化」** → 不会，必须显式 `storage_context.persist()`。
3. **「改了 Settings 就全局生效」** → 显式传参优先；先查有没有局部覆盖。
4. **「metadata 是免费的」** → 默认注入正文，影响 embedding 语义、上下文占用与成本。
5. **「切分随时能改」** → 改 chunk_size / 换 embed_model 都必须重建索引，且系统不会提醒你。
6. **「向量库解决了删除与更新」** → 需要 docstore + 稳定的 `doc_id` 才能正确 upsert / 删除。
7. **「QueryEngine 是黑盒」** → 它是三段式的显式组合，每一段都能替换。
8. **「Workflow 更高级所以更好」** → 它只是控制流的表达力更强，简单场景是纯负担。
9. **「Agent 是另一种东西」** → 0.12+ 的 Agent 就是 Workflow 的特化，异步、可流式、可观测。
10. **「异步可以随手 await」** → `agent.run` / `pipeline.arun` / `workflow.run` 都是协程，同步脚本要 `asyncio.run`。

## 14. 本章速查卡

**对象职责一句话版：**

| 对象 | 一句话 |
| --- | --- |
| `Document` | 一整份源文件（TextNode 子类） |
| `Node` | 检索与索引的最小单位（chunk + metadata + relationships） |
| `NodeParser` | Document → Node |
| `IngestionPipeline` | Node 加工流水线：切分 → 抽取 → 嵌入，带缓存与文档管理 |
| `Index` | 访问策略（向量/摘要/关键词/图），不含数据本体 |
| `StorageContext` | docstore / index_store / vector_store 的装配单 |
| `Retriever` | 只要「找到相关节点」 |
| `NodePostprocessor` | 对召回结果的过滤/重排/扩展 |
| `ResponseSynthesizer` | 节点 + 问题 → 答案（`response_mode` 控制成本） |
| `QueryEngine` | 检索 + 后处理 + 合成 的固定管道 |
| `ChatEngine` | QueryEngine 的有状态会话外壳 |
| `Settings` | 全局默认依赖（懒实例化，局部传参可覆盖） |
| `Workflow` | 事件驱动编排：步骤订阅事件、发布事件、共享 Context |
| `FunctionAgent` | Workflow 特化：LLM 选工具，循环直到完成 |

**四条架构纪律：**

1. **一条写入路径**：生产环境只用 `IngestionPipeline` 写数据，索引侧只 `from_vector_store` 挂载。
2. **一个配置入口**：`Settings` 只在启动处设，业务代码一律局部传参。
3. **先验检索再谈合成**：`response_mode="no_text"` + `source_nodes` 是你最好的调试器。
4. **控制流复杂了才上 Workflow**：QueryEngine → ChatEngine → Workflow 是能力阶梯，不是风格选择。
