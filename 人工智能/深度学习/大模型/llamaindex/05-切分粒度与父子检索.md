# 05 切分粒度与父子检索：到底返回子块还是父块

> 本章全部数字来自 `llama-index-core 0.14.26` 的实测脚本（`H:\PythonProject\PythonProject\lmtest` 下 01–06 号脚本），不是推测。
> 环境：Python 3.11.18，中文语料，`SentenceSplitter` 默认 tokenizer。

## 5.0 一句话结论

**父块从头到尾不参与向量检索。** 向量 `similarity_top_k` 只对叶子节点算，父块只在「同一父块下命中足够多的子块」时被**补进来**，它的分数是命中子块的平均分。

所以不存在「每次查询都命中父块返回」这回事。默认阈值 `simple_ratio_thresh=0.5` 下，日常查询通常只召回 1–2 个叶子，比例落在 1/4、1/5，**返回的是子块**；只有整段都相关时才会升级成父块。

如果发现自己几乎每次都想要父块，正确做法**不是**调阈值，而是**根本不用分层**——直接把 `chunk_size` 设成大块。分层的价值只在「同一份文档需要两种粒度按需切换」时成立。

## 5.1 五种切分器的默认参数（0.14.26 实测）

| 切分器 | 默认 chunk_size | 默认 overlap | 其他关键默认 |
|---|---|---|---|
| `SentenceSplitter` | 1024 | 200 | `paragraph_separator='\n\n\n'`，`include_prev_next_rel=True` |
| `TokenTextSplitter` | 1024 | 20 | `backup_separators=['\n']` |
| `MarkdownNodeParser` | 无（按标题切） | 无 | 依赖 `#` 层级 |
| `SentenceWindowNodeParser` | 无 | 无 | `window_size=3` |
| `HierarchicalNodeParser` | 无 | 无 | `chunk_sizes=[2048, 512, 128]` |

**第一个坑：1024 对中文太大了。** 250 字的中文段落用默认 1024/200 切，只产出 **1 个节点**，等于没切。中文大约 1 字 ≈ 1.1–1.5 token，1024 token ≈ 700–900 汉字。

```python
from llama_index.core.node_parser import SentenceSplitter

# 250 字中文 -> 1 个节点（等于没切）
SentenceSplitter().split_text(text)

# chunk_size=120, overlap=20 -> 134 字符 + 116 字符两块
SentenceSplitter(chunk_size=120, overlap=20).split_text(text)
```

## 5.2 第二个坑：中文别用 TokenTextSplitter 硬切

同一段中文、同样 `chunk_size=60`，两个切分器的结果完全不同：

| 切分器 | 结果 | 问题 |
|---|---|---|
| `TokenTextSplitter` | 40 / 45 / 47 字符三块 | **把词切断**：块尾是 `Node`，下一块以 `是切分后的` 开头；且有 45/47 字符的块**超过 60 token 上限** |
| `SentenceSplitter` | 53 / 30 / 51 字符三块 | 三块都是完整句子，没有断句 |

`TokenTextSplitter` 超限的原因：中文没有空格，`backup_separators=['\n']` 回退不到任何空格边界，只能硬切，切完的长度自然不受控。**语义检索不要用 TokenTextSplitter 处理中文。**

### 5.2.1 中文按句切的正确写法

```python
import re
from llama_index.core.node_parser import SentenceSplitter

splitter = SentenceSplitter(
    chunk_size=256,
    chunk_overlap=32,
    chunking_tokenizer_fn=lambda t: re.split(r'(?<=[。！？；\n])', t),
)
```

`chunking_tokenizer_fn` 先按中文标点切成句子单元，`SentenceSplitter` 再把这些句子合并到 `chunk_size` 以内，因此不会切断词或句子。

### 5.2.2 chunk_overlap 的真实机制：为什么设了 10 却等于 0

> 本节来自 `07_overlap.py`、`08_user_case.py`、`09_sentence_same.py`、`10_overlap_sweep.py` 四组实测。

**单位都是 token，但操作粒度是「切分单元」。** `chunk_size` 和 `chunk_overlap` 都按 token 计量，可 `_merge` 每次加减的是一个完整 split（句子、空格段或单字），不是单个 token。

源码（`llama_index\core\node_parser\text\token.py:196-251` 的 `_merge`）：

```python
if cur_len + split_len > chunk_size:
    chunks.append("".join(cur_chunk).strip())
    while cur_chunk and (
        cur_len > self.chunk_overlap            # 条件1：目标保留 <= overlap
        or cur_len + split_len > chunk_size     # 条件2：必须装得下下一个单元
    ):
        first_chunk = cur_chunk.pop(0)          # 从块头删掉一个完整单元
        cur_len -= len(self._tokenizer(first_chunk))
```

- 条件 1 是「尽量保留到 overlap 以内」；
- 条件 2 是「必须腾到能装下下一个单元」，**优先级更高，可以把保留区清成 0**。
- `pop(0)` 从块头逐个移除单元，剩下的才是下一块开头的重叠部分。

### 5.2.3 三种单元粒度的实测结果

同一份 109 token 文本，`chunk_size=60`、`chunk_overlap=10`：

| 切分单元 | 典型单元大小 | 实际重叠 | 结论 |
|---|---|---|---|
| 单字（纯中文 + `TokenTextSplitter`） | 1–2 token | 7–10 token | 生效 |
| 整句（`SentenceSplitter`） | 30–53 字 / 35 token | **0** | 弹掉一句就空 |
| 空格段（中英混排，中文连成一片） | 56 token | **0** | 装不下，被清空 |

### 5.2.4 关键案例：overlap 从 5 改到 50 结果一样

文本：`LlamaIndex 的数据模型只有两层。Document 是原始文档，Node 是切分后的……`

按空格切成 8 个单元，其中一个中文段 **56 token**。`chunk_size=60` 只比它大 4 token。

| overlap | 块数 | 各块 token | 相邻重叠（字符） |
|---|---|---|---|
| 0 | 3 | [22, 59, 27] | [0, 0] |
| 5 | 3 | [22, 59, 31] | [0, 16] |
| 10 | 3 | [22, 59, 31] | [0, 16] |
| 20 | 3 | [22, 59, 31] | [0, 16] |
| 50 | 3 | [22, 59, 31] | [0, 16] |

- **边界 0→1**：当前块 22 token，下一个单元 56 token，`22+56=78>60`，必须弹到 0 才装得下，所以永远是 0；
- **边界 1→2**：固定由 3 token 的 ` SentenceSplitter` 单元决定，与 overlap 数值无关。

### 5.2.5 判定公式

```
能留给重叠的额度 = chunk_size - 下一块第一个单元的大小
```

overlap 生效要同时满足两条：

1. **单元 token 数 ≤ overlap**（单元太粗，一次都留不住）；
2. **额度 ≥ 最小单元**（凑不出可留下的整单元）。

本例：`60 - 56 = 4`，而最小单元 8 token，`4 < 8` → 归零，与 overlap 设多少无关。

还有两个常见误解要澄清：

- 「overlap 会额外占用空间」——不会。重叠内容本身就是下一块的一部分，下一块始终满足 `重叠 + 新内容 ≤ chunk_size`。
- 「`overlap > chunk_size` 才会出问题」——构造时直接抛 `ValueError`（`token.py:64-68`），走不到切分。真正的问题是单元相对 chunk_size 太大。

### 5.2.6 修复方向

1. **换 `SentenceSplitter`**：按句切，单元 30–50 字，不会出现一段 55 字；
2. **加大 `chunk_size`**：让它远大于最长单元，如 256/512；
3. **把中文单元切细**：`chunking_tokenizer_fn` 按中文标点预切，或干脆按字符；
4. **别靠 overlap 保边界**：想要相邻块语义连贯，用默认的 `include_prev_next_rel=True`（Node 自带 prev/next 关系）或 `SentenceWindowNodeParser`。

一句话：**overlap 是软目标，单元粒度是硬约束；单元越粗，overlap 越接近 0。**

## 5.3 分层切分实际产出什么

`HierarchicalNodeParser.from_defaults(chunk_sizes=[256, 64])` 对约 400 字、8 个自然段的文本：

- 总节点 **10 个**；
- **2 个父块**（216 字符 / 139 字符），`CHILD` 关系分别指向 5 个 / 3 个子块；
- **8 个叶子**（38–55 字符），每个叶子通过 `NodeRelationship.PARENT` 指向所属父块；
- **只索引叶子**，父块只进 docstore，因此 embedding 成本不翻倍。

```text
父块A (216字, CHILD=5)     父块B (139字, CHILD=3)
  ├─ 叶1 (38字)              ├─ 叶6 (44字)
  ├─ 叶2 (52字)              ├─ 叶7 (49字)
  ├─ 叶3 (41字)              └─ 叶8 (55字)
  ├─ 叶4 (47字)
  └─ 叶5 (50字)
```

**结论：父块的子块数不固定，取决于内容长度。** 这一点直接决定 5.4 的合并频率。

## 5.4 AutoMergingRetriever 的判定机制

### 5.4.1 判定公式

```
ratio = 命中子块数 / 该父块的子块总数
ratio >= simple_ratio_thresh（默认 0.5）  ->  用父块替换这些子块
```

两个容易搞错的点：

1. **分母是父块的子块总数，不是 `top_k`，也不是命中总数。**
2. **比例是 per-parent 的局部比例**，不是全局比例。查询跨多个父块各命中 1 个时，每个父块各自比例都很低，**全部不合并**。

### 5.4.2 实测行为（父块子块数分别为 4 和 3）

| 命中情况 | ratio | 阈值 0.5 时 | 返回 |
|---|---|---|---|
| 4 块中命中 1 个 | 0.25 | 不合并 | 55 字叶子 |
| 4 块中命中 3 个 | 0.75 | **合并** | 213 字父块 |
| 4 块中命中 4 个 | 1.00 | 合并 | 父块 |
| 4 块中命中 3 个，阈值 0.8 | 0.75 | 不合并 | 叶子 |
| A 中 1 个 + B 中 1 个 | 0.25 / 0.33 | 都不合并 | 2 条叶子 |

**推论：父块越小，越容易触发合并。** `chunk_sizes=[512,128]` 比 `[2048,128]` 频繁得多。想更常给上下文，优先调小父块尺寸，而不是先调阈值。

## 5.5 两阶段澄清：父块为什么没有自己的分数

这是最容易被误解的地方，分两个阶段看：

**阶段一：向量检索**

- 只有叶子有向量；`similarity_top_k=4` 取的是 4 个**叶子**；
- 父块在这一步完全不存在，**不参与排序**，所以「父块分数低」这个说法本身不成立。

**阶段二：合并后排序**

- 命中的叶子按父块分组，判断 ratio；
- 触发合并的父块需要一个分数才能和其他保留叶子一起排序，于是取**命中子块的平均分**作为代理分；
- 这个平均分是「为了输出排序人为算的」，不是检索分。

实测平均分：命中子块 `0.60 / 0.58 / 0.55 / 0.52` → 父块 `0.5625`；`0.93 / 0.91 / 0.90` → 父块 `0.9133`。

## 5.6 混排实测：条数、字符、顺序都会变

构造：父块 A 命中 3/4（0.90 / 0.88 / 0.86，平均 0.88），父块 B 命中 1/3（0.95，不达标）。

```text
向量检索返回（全是叶子）:
  0.90  叶  第1段  55字
  0.88  叶  第3段  52字
  0.86  叶  第5段  57字    这三条同父，0.75 >= 0.5，合并
  0.95  叶  第9段  49字    单独父块，0.33 < 0.5，保留

合并后最终返回:
  0.9500  叶子  49字    原分保留
  0.8800  父块  213字   (0.90+0.88+0.86)/3

条数 4 -> 2，字符 213 -> 262
```

三个可观察后果：

1. **条数变少**，但**总字符变多**（父块把整段都带上）；
2. **顺序会变**：原本排第 1 的 0.90 叶子，合并后变成 0.88 的父块，让位给 0.95 的叶子；
3. 合并后的父块平均分若低于某个保留叶子，排序会大幅下滑——这就是「精确命中被稀释」的具体表现。

## 5.7 决策矩阵：子块、父块，还是不分层

真正要决策的不是「选子块还是选父块」，而是**要不要用分层切分**：

| 你的场景 | 配置 | 理由 |
|---|---|---|
| 问题总要一句/一段原文（查条款、查字段、查事实） | 纯叶子：`SentenceSplitter(chunk_size=256~512)`，不分层 | 精度优先，不需要父块 |
| 问题总要完整章节/流程/摘要 | 直接大块：`chunk_size=1024~2048`，不分层 | 你要的「父块」就是大块本身，分层纯属多余 |
| 混合型：有的要细节，有的要上下文 | 分层 `chunk_sizes=[1024,256]` + 阈值 0.5 | 让命中密度自动决定 |
| 想让父块也参与检索排序 | 双层索引 / `RecursiveRetriever` | 不推荐：向量翻倍、父块向量被长文本稀释 |

### 5.7.1 用数据决定，别拍脑袋

拿 20–30 条真实查询跑一遍，统计**输出里父块占比**：

| 父块占比 | 判断 | 动作 |
|---|---|---|
| < 20% | 分层几乎没起作用 | 砍掉分层，回退纯叶子或大块 |
| 20%–50% | 分层确实在混合场景下干活 | 保留，按需微调 `simple_ratio_thresh` |
| > 50% | 查询就是整段型 | 直接大块更省事，去掉分层 |

### 5.7.2 阈值怎么调

- `simple_ratio_thresh=0.5`（默认）：多数查询给叶子，整段相关才给父块——**推荐起点**；
- 调到 `0.3`：更容易给父块，适合「宁可多给上下文」的问答；
- 调到 `0.8`：只有几乎全命中才合并，适合精度优先；
- 调到 `0`：几乎总给父块——此时应直接删掉分层，用大 `chunk_size`，行为更可预测。

## 5.8 完整可运行代码

```python
from llama_index.core import Document, StorageContext, VectorStoreIndex, Settings
from llama_index.core.node_parser import HierarchicalNodeParser, get_leaf_nodes
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core.retrievers import AutoMergingRetriever
from llama_index.core.query_engine import RetrieverQueryEngine
from llama_index.core.llms import MockLLM
from llama_index.core.embeddings import MockEmbedding

Settings.llm = MockLLM(max_tokens=64)
Settings.embed_model = MockEmbedding(embed_dim=8)

documents = [Document(text=open('corpus.txt', encoding='utf-8').read())]

# 1) 分层切分
parser = HierarchicalNodeParser.from_defaults(chunk_sizes=[1024, 256])
nodes = parser.get_nodes_from_documents(documents)
leaf_nodes = get_leaf_nodes(nodes)          # 只索引叶子

# 2) docstore 必须装全部节点（含父块），AutoMerging 靠它按 id 取父块
docstore = SimpleDocumentStore()
docstore.add_documents(nodes)
storage_context = StorageContext.from_defaults(docstore=docstore)

# 3) 只对叶子建索引
index = VectorStoreIndex(leaf_nodes, storage_context=storage_context)

# 4) 挂自动合并
base_retriever = index.as_retriever(similarity_top_k=6)
retriever = AutoMergingRetriever(
    base_retriever, storage_context, simple_ratio_thresh=0.5
)

query_engine = RetrieverQueryEngine.from_args(retriever)
print(query_engine.query('节点和块的关系是什么？'))
```

持久化时**别只存叶子**：父块在 docstore 里，丢失后合并会静默失效。

```python
index.storage_context.persist(persist_dir='./storage')  # 含 docstore/index_store 的完整上下文
```

## 5.9 常见误用清单

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 中文用 `TokenTextSplitter` | 词被切断，块长失控 | 用 `SentenceSplitter` + 中文 `chunking_tokenizer_fn` |
| 用默认 `chunk_size=1024` 切短中文 | 整段一个节点，等于没切 | 中文按 256–512 起步 |
| 想「每次都要父块」却保留分层 | 多出一层复杂度且不可预测 | 去掉分层，直接大块 |
| docstore 只 `add_documents(leaf_nodes)` | 合并时找不到父块，静默退化为叶子 | 必须 add 全部 `nodes` |
| 调 `simple_ratio_thresh=0` 求父块 | 行为等价于大块，但多了一次检索 | 直接改 `chunk_size` |
| 期望父块出现在 `similarity_top_k` 里 | 父块没有向量，永远选不中 | 需要父块参与检索就做双层索引 |
| 对小块语料强行分层 | 父块子块数太小，合并过于频繁 | 父块子块数 ≥ 4 才有意义 |

## 本章速查

- 父块不索引、不进 `top_k`；只在合并后作为结果项出现，分数 = 命中子块平均分。
- 合并比例 = 命中子块数 / 父块子块总数，默认阈值 0.5。
- 默认阈值下多数查询返回叶子；想要父块就调小父块尺寸或阈值。
- 若「几乎每次都要父块」，删掉分层，直接大 `chunk_size`。
- 中文切分：`SentenceSplitter` + `chunk_size=256~512` + 按中文标点预切；禁用 `TokenTextSplitter`。
- docstore 必须装全部节点；持久化要带上 docstore。
